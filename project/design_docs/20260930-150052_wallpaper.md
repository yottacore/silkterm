## Summary

SilkTerm can show a faint picture behind the text. The picture is blurred and flattened so the text is still what gets read. Separately, the window can be made see-through, so the desktop shows behind the text. Both are on the Background tab.

## Specification

- The wallpaper is on by default, and something is always shown while it's on.
	- A named image wins.
	- If an image isn't named, or an image won't open, the built-in picture is used instead.

- A wallpaper named on the command line, at launch or while running, is used for that session only and is never saved. It turns the wallpaper on even when the file has it off. A performance profile that turns the wallpaper off still wins.

- When the command line doesn't name an image (`--wallpaper-file` or `--wallpaper` without a value), the session doesn't show a picture.

- Only PNG and JPEG images are read.

- Visibility sets how much of the picture's own contrast shows on screen. The same number looks the same in dark mode and light mode, and about the same for a bright photo and a dark one.

- Blur softens the picture, and the contrast mask flattens its busy parts toward its average. Both are worked out once when the image loads.

- Fit is Stretch or Zoom, Stretch by default. An image can have its own fit, crop anchor, visibility, and blur in its metadata, and those win unless their switches are off.

- Nothing about the wallpaper can delay the window. The window opens and the shell starts at once, and the picture appears when it's ready.

- The see-through window is off by default. Opacity sets how much of the desktop shows through the background. Text, chrome, and the cursor stay opaque. Blur-behind asks the compositor to blur what's behind the window, where the compositor supports it. On Windows a change to transparency takes effect at the next launch.

## Goals

- The terminal looks good without getting in the way of reading.

- A setting means the same thing in every mode and for every picture.

- A wallpaper on a slow or dead network share must never stop the terminal from opening.

- The file doesn't have any surprises. Automatic choices aren't written back.

### Non-goals

- The picture isn't meant to be the main focus. The wallpaper stays faint by default, as a backdrop.

- SilkTerm doesn't read every image format. Each decoder adds to the binary for a rare case.

- SilkTerm doesn't blur the desktop behind a see-through window itself. That's the compositor's job.

## Design

### The pipeline runs on a worker

Nothing on the path from launch to the first frame may read an external resource that isn't needed to draw that frame. A wallpaper folder can be a network share, a synced collection, or anything else that responds slowly or times out. A terminal that waits for it hasn't opened yet.

- The wallpaper is the only thing in that category today. That's decoding the image, blurring it and flattening its contrast, and reading its layout tags. All of it runs on a worker thread. The window opens and the shell starts at once, and the wallpaper appears when it's ready. That visible gap is an accepted trade-off, since otherwise the window might never open at all.

- Each request gets its own thread rather than sharing a long-lived worker. A request stuck on a dead mount can never be canceled, so a shared worker would leave every later request stuck behind it. A stale result is thrown away on arrival, and a thread stuck on a read costs almost nothing. A thread that's doing real work costs a lot more. So between its stages, a superseded worker checks whether it's still the newest, and gives up when it isn't. Those checks come before the float copy and the blur, which use most of the memory and time.

- Images are cut down to 4096 pixels on a side in their own pixel format before the RGBA copy, and before the blur. The decode is capped at 512 MiB. An image that's past the GPU's size limit doesn't abort anymore.
	- Since 2026-10-05 the picture is then stored at the size it's drawn at in the window, and prepared again once a resize stops. See [The wallpaper at window size](20261004-182255_reduce-resources.md#the-wallpaper-at-window-size).

- The shell scan waits for the wallpaper to be on screen, rather than only the window, so it doesn't compete with the first picture. If the wallpaper takes too long, a deadline starts the scan anyway.

- A settings reload keeps the current image. Reload config always reads the image file again, and Apply reads it again only when the setting changed.

### Where the picture comes from

- With the wallpaper switched on, something is always shown. The built-in image is used whenever there isn't another one, because an image isn't named or a file won't open.
	- The one exception is when none is asked for. With `--wallpaper-file` or `--wallpaper` without a value, the session doesn't show a picture.

- The built-in image is compiled in byte for byte, and goes through the same blur, contrast mask, and visibility as any other image.

- A path in the wallpaper setting follows these rules.
	- On Windows a rooted path without a drive letter resolves against the config folder's drive.
	- Paths may start with `~` and use any of the 3 ways to write a variable.

- A wallpaper named on the command line, at launch or while running, turns the wallpaper on for the session even when the file has it off. Naming one is a deliberate choice. A performance profile that turns the wallpaper off still wins, since the profile is applied after the command line. Reload config keeps it. `--wallpaper` on a running window is sent over its control socket, which is a named pipe on Windows.

### How much of the wallpaper is on screen

The visibility slider is an amount a person chose, but the renderer needs a linear-light alpha. Those aren't the same thing, in 2 separate ways, and both used to show on screen.

The first is the mode. sRGB's curve is steep near black and flat near white, so the same alpha makes a big visible change over a dark background and almost none over a light one. At the default of 10%, a picture's own contrast measured 6.4 sRGB levels of spread in dark mode and 0.6 in light. With the same setting, the picture couldn't be seen in light mode.

The first thing to settle is what the slider means. It means **this much of the picture's own contrast reaches the screen**. Over a black background a linear blend delivers exactly that, because black leaves the blend a pure scale of the encoded picture, and a scale can't change contrast. That's why dark mode never needed any of this, and the closed form `alpha^(1/2.4)` gives how much it delivers. A dark theme whose background isn't black delivers less, and the same expression says how much less.

Light mode can't deliver it with a blend at all, so it doesn't use one. It mixes the background and the picture in a power curve, at the amount dark mode's blend would have delivered. The curve is a pure power rather than sRGB's own, because sRGB's `- 0.055` term doesn't cancel. Over black the power curve makes the mix exactly the linear blend it replaces, so the two modes are one rule with dark mode as its black-background case. sRGB's curve would have lifted dark mode's black by 8 levels. After the change, light mode's spread measured 6.4 against dark mode's 6.4, and at half visibility 12.5 against 12.5.

A mix needs the background color, which a hardware blend can't supply, so the wallpaper pass writes the pane fill itself and is clipped to the pane. The divider slits between panes keep their own color rather than taking a faint tint from the picture.

The second is the picture. At one setting a bright photo glares where a dark one is barely there, because the slider says how much of the picture to mix in rather than how far to move the background. `wallpaper.even_visibility` gives every picture the same displacement. A picture that's further from the background than the median of the default pack is drawn at less than the number says, and one that's closer is drawn at more. How bright a picture looks is half its overall level and half its bright end, because glare comes from the bright end. A night sky with a sun in it doesn't look like a dark picture. The correction fades out as the slider rises and is gone at 100%, since that's where the picture has to be drawn as it is.

The correction applies to dark mode too, which is the point of it. At a 10% slider the pack's brightest picture went from a mean of 58.8 to 48.3, and its darkest from 0.8 to 2.6. In light mode the rule works from the other side, because there the dark picture is the one that stands out. The same two went from 26 and 93 sRGB levels of displacement to 63 and 52. Setting it to 0 gives the old behavior exactly.

In light mode the scrim's halo is matched to dark mode's over the same picture. See the [Text scrim](20260930-145304_scrim.md) design doc.

Everything here is measured with a transfer curve on Rec.709 luma. Luma is used because a linear-light alpha blend is affine in it, so one number can represent a whole composite. A curve is used because the eye doesn't see in linear light. The sRGB transfer tracks CIE L* closely enough for the scrim, and the pure power is what makes the mix exact. Oklab lightness was measured and rejected. It doesn't have a linear toe, so it rates a near-black background as far more separable than it is.

The pipeline contract hasn't changed. The wallpaper pass still emits linear light, and only the mix inside it is done in a curve. Everything downstream, including the scrim, the text, and the cursor, only sees linear light.

### Blur, banding and the contrast mask

- The blur runs in source-image space, before the fit, and in linear light.
	- Its sigma is in pixels of the image after the 4096 cut. A picture that's stored smaller than that is shrunk in linear light first, and the blur and the contrast mask's busyness are scaled to match.

- The picture is drawn through a 16-bit float offscreen, with a dither of about 1 level before the 8-bit write. An 8-bit linear offscreen showed banding in smooth gradients.

- The contrast mask is computed once at load. It flattens the picture toward its mean rather than darkening it. It has its own switch plus Size, Strength, and an Automask mix, which blends the manual values with values taken from how busy the image is.

### Layout and look tags

A wallpaper image can have its own layout and look in its XMP metadata, under a `wallpaper` namespace. The namespace is named for what the tags describe rather than for this program, so any tool can write them.

- `Fit` (stretch or zoom) and `Anchor` (a percentage pair) are absolute, since how an image should be cropped is a property of the image. The anchor chooses what a zoom crop keeps.

- `Opacity` and `Blur` are absolute too, in the same units as the 2 settings, and replace them for that image.

- Each pair has its own switch in Settings, "Honor layout tags" and "Honor look tags", both on by default.

- A missing or unreadable tag always falls back to the setting rather than failing the image.

- Every image in the default pack is tagged with the program defaults, 10% and 10. So the 2 sliders only affect untagged images, unless the look switch is turned off. That trade-off was accepted so an image's look means the same thing everywhere.
	- As of 2026-10-07, the switch stays on by default and the pack keeps its tags. The flyovers on both sliders and on the switch say that a tag wins while the switch is on.

### The see-through window

- It's opt-in (`transparency.enabled`). `transparency.opacity` sets how much of the background is drawn, 0.95 by default. Text, window decorations, the bars, and the cursor stay opaque.

- On X11, wgpu can't drive a see-through surface. The Vulkan swapchain forces an opaque one, and wgpu's GL backend won't bind an ARGB visual. So a GL context with an ARGB visual is made by hand through glutin, the scene is rendered to an offscreen texture, and that's copied to the window. glyphon doesn't draw any text on NVIDIA below GL 4.2, so the context requests 4.6 and falls back as low as 3.3.

- On Wayland the surface already has premultiplied alpha, so the ordinary path works.

- On Windows, transparency means presenting through the desktop compositor. That's a DX12 swapchain on a DirectComposition visual, without any redirection surface under the window. A swapchain that's made straight from the window only composites opaque, and the backend picked by default varies by machine, so DX12 is pinned whenever the setting is on. Both are fixed when the window is made, so the setting takes effect at the next launch there. If it fails, the window falls back to opaque with a notice. The no-redirection style is requested only when transparency is on, because virtual desktop managers skip such windows.

- Without a compositor, it doesn't do anything.

- Blur-behind (`transparency.blur_behind`) is a hint to the compositor, through a stable window class, for KWin and picom. It's separate from the wallpaper's own blur.

- A light fill lets through as much of the desktop as a dark one at the same opacity. The fill used to be encoded to sRGB after it was premultiplied, so a light fill at 80% came out as 91% of itself.

- The frame is cleared opaque unless transparency is on.

### The pack and the gallery

- The default pack is 102 images in `filesystem/home/.config/silkterm/wallpaper`. Each is recorded in `wallpaper-attribution.md` with its source and how certain that source is. Images with legal doubt, or a vendor's image without a redistribution license, were taken out.

- Every image in the pack is tagged with the program defaults.

- The wallpaper gallery is a page on GitHub Pages, served from main's `docs/`, and it's only updated on a release. It has thumbnails only and fetches each full image from the pack. The gallery and the README contact sheet are both made by `cicd/utility/wallpaper-gallery.bash`. See [Delivery](../design.md#delivery-cicd-branches-releases) in `design.md`.

## Alternative ideas

### Unconsidered

- "Minority Report" mode, which is borderless and see-through, with a perspective tilt that follows the window's place on the screen. Backlog: "Feature: Minority Report mode" (deferred, Opened 20260703-071620).

### Rejected

- More image formats. Each extra decoder costs binary size. Backlog: "Wallpaper scan accepts formats that can't be loaded".

- A shared long-lived worker for wallpaper requests. A request stuck on a dead mount can never be canceled, so every later one would wait behind it.

- Oklab lightness for the visibility measures. It rates a near-black background as far more separable than it is.

- Disabling the idle GPU release under transparency. The X11 GL path survives it. See the [Releasing resources](20260930-151334_releasing-resources.md) design doc.

### Superseded

- A light-mode calibration (`lightmode.rs`, `PRESENCE`) that scaled the picture's alpha to look right in light mode. The power-curve mix replaced it, and that mix makes the 2 modes one rule. Backlog: "Dark mode is just about perfect, so don't make ANY changes that affect dark mode. But light mode is badly miscalibrated" (closed 20260920).

- The flat `background_*` and `wallpaper_*` keys. They're nested under `wallpaper.` and `transparency.` now, and the old names still convert.

- A `backgrounds/` then `wallpapers/` folder. The folder is `wallpaper/`, and both older names are still found.

- Zoom as the default fit. It's Stretch now. A blur of 0, then 8, and it's 10 now. An opacity of 33%, and visibility is 10% now.

## Research findings

- sRGB is steep near black, so the same linear alpha does little over a light background. At 10%, a picture's own contrast came out at 6.4 levels in dark mode and 0.6 in light.

- Launch to a visible window went from about 2.5 s to about 0.3 s with a 4K image, once the wallpaper was moved to a worker.

- An 8000 by 8000 image used 869 MiB before it was cut down, and 141 MiB after. A 45-megapixel photo went from over 2 GB to under 1 GB.

- Reverse image lookups for attribution mostly find reposts or dead links. A filename prefix marks a collection, never authorship.

## Roadmap

- Offer to copy the wallpaper pack into place on a first run without a config or a wallpaper folder, with a matching button in Help > About. The wording is written. Backlog: "At startup, offer to copy the wallpaper pack from the repo to the local wallpaper directory" (Opened 20260817-120024).

- A wallpaper, font, and colors per pane. That needs a renderer per pane, but there's only one text context today. Backlog: "Command-line options" (Opened 20260628-083740).

- The see-through window hasn't been checked on Windows under a real compositor recently, and Wayland transparency isn't in the test runs.
