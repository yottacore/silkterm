## Summary

SilkTerm can show a picture behind the text, faintly, blurred and flattened so the text stays the thing that is read. The picture can rotate through a folder, and it can supply the text colors. Separately, the window can be made see-through, so the desktop shows behind the text. Both live on the Background tab.

## Specification

- The wallpaper is on by default, and something is always shown while it is on.
	- A named image wins.
	- Otherwise a folder of images rotates.
	- If no image is named and the folder is empty or missing, or an image will not open, the built-in picture stands in.

- A wallpaper named on the command line, at launch or while running, is used for that session only and never saved. It turns the wallpaper on even when the file has it off, and it stops rotation for the session. A performance profile that turns the wallpaper off still wins.

- Naming no image on the command line (`--wallpaper-file` or `--wallpaper` with no value) shows no picture for the session.

- Rotation picks a new image from the folder at each launch, or on a timer when an interval is set. It shuffles the way a music player does: random, but never one of the recently shown. Plain filename order is a setting. "Next wallpaper" on the menu moves on at once, and shows only when the folder has another image.

- The default folder is the platform's usual place: `%LOCALAPPDATA%\silkterm\wallpaper` on Windows, `$HOME/Library/Application Support/silkterm/wallpaper` on macOS, and `$XDG_CONFIG_HOME/silkterm/wallpaper` elsewhere. A folder there with images in it is taken as wanting rotation, and nothing is written to the file to say so.

- Only PNG and JPEG images are read.

- Visibility sets how much of the picture's own contrast reaches the screen. The same number looks the same in dark mode and light mode, and about the same for a bright photo and a dark one.

- Blur softens the picture, and the contrast mask flattens its busy parts toward its average. Both are worked out once when the image loads.

- Fit is Stretch or Zoom, Stretch by default. An image can carry its own fit, crop anchor, visibility and blur in its metadata, and those win unless their switches are off.

- With "Text colors from the wallpaper" on, the text and cursor colors come from the picture. The derived text is never dimmer than the theme's, and none of it is written to the file. It is on by default.

- Nothing about the wallpaper may delay the window. The window opens and the shell starts at once, and the picture appears when it is ready.

- The see-through window is off by default. Opacity sets how much of the desktop shows through the background. Text, chrome and the cursor stay opaque. Blur-behind asks the compositor to blur what is behind the window, where it can. On Windows a change to transparency takes effect at the next launch.

## Goals

- A terminal that looks good without getting in the way of reading.

- One setting that means the same thing in every mode and for every picture.

- A wallpaper on a slow or dead network share must never stop the terminal opening.

- No surprises in the file. Automatic choices, such as rotation or derived colors, are not written back.

### Non-goals

- A picture as the main event. The wallpaper stays faint by default. It is a backdrop.

- Every image format. Each decoder adds to the binary for a rare case.

- Blurring the desktop behind a see-through window ourselves. That is the compositor's job.

## Design

### The pipeline runs on a worker

Nothing on the path from launch to the first frame may read an external resource that is not needed to draw that frame. A wallpaper folder can be a network share, a synced collection or anything else that answers slowly or times out, and a terminal that waits for it is a terminal that has not opened yet.

- The wallpaper is the whole of that category today: scanning the rotation folder, reading the shuffle history, decoding the image, blurring and contrast-flattening it, and reading its layout tags. All of it runs on a worker thread. The window opens and the shell starts at once, and the wallpaper appears when it is ready. That visible gap is an accepted trade, since the alternative is a window that may never open at all.

- Each request gets its own thread rather than sharing a long-lived worker. A request stuck on a dead mount can never be canceled, so a shared worker would leave every later request stuck behind it. A stale result is thrown away on arrival, and a thread stuck on a read costs almost nothing. One doing real work does not, so a superseded worker asks between its stages whether it is still the newest, and gives up when it is not, before the float copy and the blur where most of the memory and time go.

- A rotation tick that finds a request still working sends nothing. Sending would only retire the one in flight, and once an image took longer to prepare than the interval, every rotation was retired before it arrived: the picture never changed, and the retired workers ran on, several gigabytes at once. The tick is remembered and served by the arriving result. So an interval shorter than a preparation rotates at the pace of the preparation, with one worker at a time, and the setting reads as "at least this many seconds".

- Images are cut down to 4096 pixels on a side in their own pixel format before the RGBA copy, and before the blur. The decode is capped at 512 MiB. An image past the GPU's size limit no longer aborts.
	- Since 2026-10-05 the picture is then held at the size the window draws it at, and prepared again once a resize stops. See [The wallpaper at window size](20261004-182255_reduce-resources.md#the-wallpaper-at-window-size).

- The shell scan waits for the wallpaper to be on screen, not merely the window, so it does not compete with the first picture. A deadline backstop starts it anyway.

- A settings reload keeps the current image. Reload config always reads the image file again, and Apply reads it again only when the setting changed.

### Where the picture comes from

- With the wallpaper switched on, something is always shown. The shipped image stands in whenever nothing else supplies one: no image named, an empty rotation folder, a file that will not open. A folder that does have images owns the picture instead, so the stand-in only appears once the folder has been read and found wanting. So any request that could leave the window bare has to read the folder first, rather than assume the last pick is still in hand.
	- The one exception is asking for none. `--wallpaper-file` or `--wallpaper` with no value shows no picture for the session, with or without a rotation folder.

- The built-in image is compiled in byte for byte, and runs through the same blur, contrast mask and visibility as any other.

- A folder of wallpapers sitting in the expected place is taken as wanting them rotated, without a setting to turn it on and without writing anything back. The inference yields to anything explicit: a wallpaper named in the config, or one given on the command line.
	- The folder setting's default names that place the way somebody on the platform would type it. It used to be blank, and a blank box says nothing about what goes in it. The default is looked up as "the usual place" rather than expanded. So it still finds the older `wallpapers` and `backgrounds` spellings and a pack left beside the config on Windows, and it follows `--config` and `XDG_CONFIG_HOME`. An empty value means the same.
	- On Windows a rooted path with no drive letter resolves against the config folder's drive.
	- Paths may start with `~` and use any of the three variable spellings.

- Settings has one "File or folder" box for both. A named image wins at run time, so the box shows one whenever it is set. Otherwise it follows Rotate folder: the folder with it on, the image with it off. Which of the two a field edits is fixed when the field opens, so emptying it on the way to typing something else does not switch it.

- A wallpaper named on the command line, at launch or while running, turns the wallpaper on for the session even when the file has it off. Naming one is a deliberate choice. A performance profile that turns the wallpaper off still wins, since the profile goes on after the command line. Reload config keeps it. `--wallpaper` on a running window goes over its control socket, which exists on Linux and Unix only.

### Rotation

- `wallpaper.rotate.interval_s` of 0 picks once at launch.

- The shuffle never repeats a recently shown image. The history is kept in `.wallpaper-history` beside the config. `wallpaper.rotate.random: false` gives filename order.

- The folder is scanned again on each change, so images added while running are picked up.

- "Next wallpaper" restarts the rotation timer from the new pick. A command-line wallpaper hides it.

### How much of the wallpaper is on screen

The visibility slider is an amount a person chose, and what the renderer wants is a linear-light alpha. Those are not the same thing, in two separate ways, and both used to show.

The first is the mode. sRGB's curve is steep near black and flat near white, so the same alpha covers a lot of visible ground over a dark background and almost none over a light one. Measured at the shipped 10%, a picture's own contrast came out at 6.4 sRGB levels of spread in dark mode and 0.6 in light. Same setting, and the picture was simply gone.

What the slider means is settled first: **this much of the picture's own contrast reaches the screen**. Over a black background a linear blend delivers exactly that, because black leaves the blend a pure scale of the encoded picture, and a scale cannot touch contrast. That is why dark mode never needed any of this, and the closed form `alpha^(1/2.4)` says how much it delivers. A dark theme whose background is not black delivers less, and the same expression says how much less.

Light mode cannot deliver it with a blend at all, so it does not use one. It mixes the background and the picture in a power curve, at the amount dark mode's blend would have delivered. The curve is a pure power rather than sRGB's own, because sRGB's `- 0.055` term does not cancel. Over black the power curve makes the mix exactly the linear blend it replaces, so the two modes are one rule with dark mode as its black-background case. sRGB's curve would have lifted dark mode's black by eight levels. Measured after the change, light mode's spread was 6.4 against dark mode's 6.4, and at half visibility 12.5 against 12.5.

A mix needs the background color, which a hardware blend cannot supply, so the wallpaper pass writes the pane fill itself and is clipped to the pane. The divider slits between panes keep their own color rather than taking a faint tint from the picture.

The second is the picture. At one setting a bright photo glares where a dark one is barely there, because the slider says how much of the picture to mix in rather than how far to move the background. `wallpaper.even_visibility` gives every picture the same displacement. One further from the background than the shipped pack's median is drawn at less than the number says, and one closer at more. How bright a picture reads is its overall level and its bright end together, half each, because glare comes from the bright end. A night sky with a sun in it is not a dark picture to look at. The correction fades out as the slider rises and is gone at 100%, since that is where the picture has to be drawn as it is.

It reaches dark mode too, which is the point of it. At a 10% slider the pack's brightest picture went from a mean of 58.8 to 48.3, and its darkest from 0.8 to 2.6. In light mode the rule reads from the other side, because there it is the dark picture that stands out. The same two went from 26 and 93 sRGB levels of displacement to 63 and 52. Setting it to 0 gives the old behavior exactly.

In light mode the scrim's halo is matched to dark mode's over the same picture. See the [Text scrim](20260930-145304_scrim.md) design doc.

Everything here measures with a transfer curve taken on Rec.709 luma. Luma, because a linear-light alpha blend is affine in it, so one number stands in for a whole composite. A curve, because linear light is not what the eye reads. The sRGB transfer tracks CIE L* closely enough for the scrim, and the pure power is what makes the mix exact. Oklab lightness was measured and rejected: it has no linear toe, so it reads a near-black background as far more separable than it is.

The pipeline contract stays: the wallpaper pass still emits linear, and only the mix inside it happens in a curve. Nothing downstream, not the scrim, the text or the cursor, sees anything but linear light.

### Blur, banding and the contrast mask

- The blur runs in source-image space, before the fit, and in linear light.
	- Its sigma is in pixels of the image after the 4096 cut. A picture held smaller than that is shrunk in linear light first, and the blur and the contrast mask's busyness are scaled to match.

- The picture is drawn through a 16-bit float offscreen, with a dither of about one level before the 8-bit write. An 8-bit linear offscreen showed banding in smooth gradients.

- The contrast mask is computed once at load. It flattens the picture toward its mean rather than darkening it. It has its own switch plus Size, Strength and an Automask mix, which blends the manual values with values taken from how busy the image is.

### Layout and look tags

A wallpaper image can carry its own layout and look in its XMP metadata, under a `wallpaper` namespace named for what the tags describe rather than for this program, so any tool can write them.

- `Fit` (stretch or zoom) and `Anchor` (a percentage pair) are absolute, since how an image should be cropped is a property of the image. The anchor chooses what a zoom crop keeps.

- `Opacity` and `Blur` are absolute too, in the same units as the two settings, and replace them for that image.

- Each pair has its own switch in Settings, "Honor layout tags" and "Honor look tags", both on by default.

- A missing or unreadable tag always falls back to the setting rather than failing the image.

- The shipped pack carries the program defaults on every image, 10% and 10. So the two sliders only reach untagged images until the look switch is turned off. That trade was accepted so an image's look means the same thing everywhere.
	- Settled 2026-10-07: the switch stays on by default and the pack keeps its tags. The flyovers on both sliders and on the switch say that a tag wins while the switch is on.

### Text colors from the wallpaper

A switch on the Themes tab takes the text and cursor colors from the picture behind them instead of from the theme. It is on by default, since the wallpaper is on by default too, and the derived text is never dimmer than the theme's own. So it can only help, and with no picture up it does nothing. While it is on, the Foreground and Cursor rows gray out, and nothing derived this way is written to the file. A rotation would otherwise rewrite the config every few minutes, and the colors would outlive the picture they came from.

Two halves, worked out separately. Harmony and legibility are unrelated problems, and one number cannot answer both. A complement at the same lightness as its ground is the least readable pairing there is, which is where the shimmer at the edge of vivid opposites comes from.

- **Lightness** comes from how bright the background actually gets. This is the half that does the work, and the obvious approach is the wrong one. Averaging the image says nothing useful, because a photo's brightness varies from cell to cell, and text readable over a dark sky vanishes into a cloud. The text is placed the contrast floor away from the field's bright end: the 95th percentile of the cells behind it, once the picture has been composited over the theme's background at its visibility setting.

- **Hue** comes from the picture's own dominant hue, turned to its complement and kept to a gentle tint. A mean color cannot supply it either, for a different reason. Opposite hues cancel, so a picture full of color averages to gray, and the hue of that gray is noise. The hue is taken from a chroma-weighted histogram instead, the way a picture's color is normally found.

- **The cursor** takes a further third of the circle, which is where every built-in theme's cursor already sits against its foreground. Its plate is a second background the text has to clear the floor on, so the plate is placed exactly the floor away from the text, the furthest it can get from the picture while still carrying a glyph. The cursor that draws it is found from there.

Three limits:

- **It cannot guarantee the floor, and does not pretend to.** Past a point no color exists, since the picture's own bright end is already inside the floor of white. The derived color takes the best position available and the text scrim covers the rest, which is the job the scrim already had. Nothing else is switched on behind the user's back to make up the difference.

- **A dark picture never dims the text.** The theme says how bright its text should be, and the picture may only ask for more. Without that floor a near-black wallpaper answers mid-gray text, which reads as the wallpaper spoiling the theme.

- **The theme still decides which side the text sits on.** A light theme keeps dark text however dark the picture is. Flipping polarity from a photograph would stop it being the theme that was chosen.

The chroma is capped low for every theme, which is the one place a theme's own identity is overridden on purpose. Carrying a monochrome theme's saturation to a complementary hue turns Matrix's green into flat yellow. The tint is decoration and the lightness is the legibility, so the tint is what gives way. A picture with almost no color in it keeps the theme's own hue instead, since there is nothing to complement.

The grayed rows show the user's own colors, not the derived pair. A row a performance profile governs shows the profile's value, because there is no other way to see it. A color is different, since it is on screen behind the dialog. So the rows say what comes back when the switch goes off, and the derived pair never reaches the dialog, the file or a saved theme.

The work is split across two threads. The wallpaper worker already has the finished pixels, so it reduces the picture to six numbers there. The colors are worked out from those numbers wherever the live settings are, which is what lets a theme change re-color the text with no second decode. Luma is what gets summarized rather than lightness, because luma survives being composited over a background color later and lightness does not.

### The see-through window

- It is opt-in (`transparency.enabled`). `transparency.opacity` sets how much of the background is drawn, 0.95 by default. Text, window decorations, the bars and the cursor stay opaque.

- On X11, wgpu cannot drive a see-through surface: the Vulkan swapchain forces an opaque one, and wgpu's GL backend will not bind an ARGB visual. So a GL context with an ARGB visual is made by hand through glutin, the scene renders to an offscreen texture, and that is copied to the window. glyphon draws no text on NVIDIA below GL 4.2, so the context asks for 4.6 and falls back as low as 3.3.

- On Wayland the surface already carries premultiplied alpha, so the ordinary path works.

- On Windows it means presenting through the desktop compositor: a DX12 swapchain on a DirectComposition visual, with no redirection surface under the window. A swapchain made straight from the window only composites opaque, and the backend picked by default varies by machine, so DX12 is pinned whenever the setting is on. Both are fixed when the window is made, so the setting takes effect at the next launch there. If it fails, the window falls back to opaque with a notice. The no-redirection style is asked for only when transparency is on, because virtual desktop managers skip such windows.

- Without a compositor, it does nothing.

- Blur-behind (`transparency.blur_behind`) is a hint to the compositor, through a stable window class, for KWin and picom. It is separate from the wallpaper's own blur.

- A light fill lets through as much of the desktop as a dark one at the same opacity. The fill used to be encoded to sRGB after it was premultiplied, so a light fill at 80% came out as 91% of itself.

- The frame is cleared opaque unless transparency is on.

### The pack and the gallery

- The shipped pack is 102 images in `filesystem/home/.config/silkterm/wallpaper`. Each is recorded in `wallpaper-attribution.md` with its source and how sure that is. Images with legal doubt, or a vendor's with no redistribution license, were taken out.

- Every image in the pack is tagged with the program defaults.

- The wallpaper gallery is a page on GitHub Pages, served from main's `docs/`, and moves only on a release. It has thumbnails only and fetches each full image from the pack. It and the README contact sheet both come out of `cicd/utility/wallpaper-gallery.bash`. See [Delivery](../design.md#delivery-cicd-branches-releases) in `design.md`.

## Alternative ideas

### Unconsidered

- "Minority Report" mode: borderless and see-through, with a perspective tilt that follows the window's place on the screen. Backlog: "Feature: Minority Report mode" (deferred, Opened 20260703-071620).

### Rejected

- More image formats. Each extra decoder costs binary size. Backlog: "Wallpaper scan accepts formats that can't be loaded".

- A shared long-lived worker for wallpaper requests. A request stuck on a dead mount can never be canceled, so every later one would wait behind it.

- Oklab lightness for the visibility measures. It reads a near-black background as far more separable than it is.

- Averaging the picture for derived text colors, for lightness or for hue.

- Disabling the idle GPU release under transparency. The X11 GL path survives it. See the [Releasing resources](20260930-151334_releasing-resources.md) design doc.

### Superseded

- A light-mode calibration (`lightmode.rs`, `PRESENCE`) that scaled the picture's alpha to look right in light mode. Replaced by the power-curve mix, which makes the two modes one rule. Backlog: "Dark mode is just about perfect, so don't make ANY changes that affect dark mode. But light mode is badly miscalibrated" (closed 20260920).

- Derived text colors off by default. They are on by default. Backlog: "Option: Dynamic text theme based on wallpaper" (Opened 20260804-134813).

- The flat `background_*` and `wallpaper_*` keys. They are nested under `wallpaper.` and `transparency.` now, and the old names still convert.

- A `backgrounds/` then `wallpapers/` folder. The folder is `wallpaper/`, and both older names are still found.

- A command-line wallpaper that let scheduled rotation carry on. It stops rotation for the session now. Backlog: "Option to rotate background images from a folder".

- Zoom as the default fit. It is Stretch. A blur of 0, then 8. It is 10. An opacity of 33%. Visibility is 10%.

- "Never repeat the image already up." The shuffle now avoids a recent history, not just the last one.

## Research findings

- sRGB is steep near black, so the same linear alpha does little over a light background. At 10%, a picture's own contrast came out at 6.4 levels in dark mode and 0.6 in light.

- One derived foreground clears a 45% contrast gap on every pack image at 10% visibility, on about two thirds at 35%, and on a fifth at 100%.

- Of the 104 wallpapers in the pack at the time, 17 averaged to something near gray, and one read 174 degrees away from the hue that was all over it.

- Launch to a visible window went from about 2.5 s to about 0.3 s with a 4K image, once the wallpaper moved to a worker.

- An 8000 by 8000 image cost 869 MiB before cutting it down first, and 141 MiB after. A 45-megapixel photo went from over 2 GB to under 1 GB.

- Reverse image lookups for attribution mostly find reposts or dead links. A filename prefix marks a collection, never authorship.

## Roadmap

- Offer to copy the wallpaper pack into place on a first run with no config and no wallpaper folder, with a matching button in Help > About. The wording is written. Backlog: "At startup, offer to copy the wallpaper pack from the repo to the local wallpaper directory" (Opened 20260817-120024).

- Randomize on a new window, tab or pane, with an interval from one second to a week. Backlog: "Wallpaper control enhancements" (Opened 20260724-080316).

- Minimum and maximum contrast and saturation as a function of visibility. Same backlog item.

- A wallpaper, font and colors per pane. Needs a renderer per pane, and there is one text context today. Backlog: "Command-line options" (Opened 20260628-083740).

- The see-through window has not been checked on Windows under a real compositor recently, and Wayland transparency is not in the test runs.
