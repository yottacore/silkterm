## Summary

SilkTerm does not fork the Alacritty terminal. It uses Alacritty's engine, the `alacritty_terminal` crate, as a library for the hard, correctness-critical parts: the PTY, the escape sequence parser and the grid. Everything a person sees is SilkTerm's own. The engine is carried on a small patched branch with five changes over its release, and two other crates, `x11-clipboard` and `glyphon`, are patched the same way.

## Specification

- The engine owns the terminal's state: the PTY, the parser, the character grid, the scrollback and the cursor. Nothing else keeps a copy of the grid's contents.

- The engine knows only whole lines. All smooth motion is done in SilkTerm's renderer.

- A patched crate is a branch under `jim-collier`, named for the published release it sits on, holding that release plus our change and a test for it. It is used through `[patch.crates-io]` in the workspace `Cargo.toml`.

- A release bump moves every change onto a new branch named for the new release. The old branch is left standing so an older lock still resolves.

- The patched engine carries five changes: the scroll ledger, the Windows reader freeze fix, a cap of nine combining marks per cell, the PTY hang-up poll, and the title and handle fixes. See Design.

- Tests for a patched change run in the fork's own repo, not in SilkTerm's pipeline.

## Goals

- Build only what makes SilkTerm different, the renderer, and take the parser and grid from a well-tested library.

- Keep every change to someone else's code small, read in full, and pinned by a test.

- Be able to take an upstream release by moving a handful of commits.

### Non-goals

- A fork of the Alacritty application. Its renderer is built to snap to cells, and smooth scrolling is out of scope for it upstream.

- A hard fork of the engine for speed. Owning the parser, reflow and the Windows console layer means owning the riskiest code for the least gain.

## Design

### Why a crate and not a fork

- `alacritty_terminal` provides the PTY, a full VT and ANSI parser, and the grid as a standalone library. It was 0.15.0 when this was designed, and is 0.26 as built. That gives SilkTerm the two hardest, correctness-critical pieces.

- Forking the Alacritty application would mean fighting its architecture, whose renderer is built to snap to cells, and carrying merge debt forever. Using the crate means a clean dependency, and building only the renderer.

- The language followed from the crate. Go (`aminal` or custom) had too little existing plumbing, and the parser is the hard part. Zig with libvterm and raylib was workable but had less ecosystem glue. Python was left out as not compiled.

### How the engine is used

- Each pane embeds an `alacritty_terminal::Term`. A reader thread per pane reads the child's PTY, feeds the bytes into that `Term`, and wakes the UI thread with a single notice. See the [Speed](20260930-150643_speed.md) design doc.

- `Term::scroll_display(Scroll)` moves the view by whole lines: `Delta(i32)`, `PageUp`, `PageDown`, `Top`, `Bottom`.

- `grid.display_offset()` is the view's whole-line offset from the bottom.

- The grid's visible cells are the source for every frame. The text is compared row by row, rather than using the engine's damage report, which misses a line rewritten with identical content.

- `config::Scrolling` is the history limit and a line multiplier. It has nothing to do with animation.

- The critical constraint: `display_offset` is whole lines, with no fraction. Smooth scrolling lives entirely in the renderer. See the [Smooth scrolling](20260930-144720_smooth-scrolling.md) design doc.

- The engine is generic over its terminal type, so SilkTerm wraps the terminal and scans the bytes on their way to the parser for the shell's directory reports (OSC 7 and OSC 9;9). That needed no fork.

- Alternate-scroll mode is on by default in the engine, so SilkTerm decides itself when the wheel sends arrow keys.

- The engine sets `TERM=alacritty` only when that terminfo entry exists locally, and `xterm-256color` otherwise. `COLORTERM=truecolor` is always set. A remote host over ssh gets whatever TERM ssh forwards.

- The word separators in the config feed the engine's `semantic_escape_chars`.

- A pane is at least two columns, the engine's documented minimum.

### The changes carried on the engine

All five sit on one branch, `scroll-ledger-0.26.0`, cut from the release tag rather than the upstream default branch. That is so the version still reads 0.26.0: cargo silently ignores a patch whose version does not satisfy the dependency requirement, and the default branch carries a pre-release version that does not.

- **The scroll ledger.** The engine records every region scroll as it happens: how many lines, which rows moved, and the rows that left the screen. It also counts every line it sends off the top into the scrollback: a whole-screen scroll, a scroll of a region starting at the top row, and a clear. A scroll of a region that shares rows with the one in flight carries on, and the ledger narrows to the shared rows. The outgoing row is taken and a spare left in its place, so nothing is copied. Both counters saturate rather than overflow. This is what lets full-screen programs, tmux included, scroll smoothly. See the [Smooth scrolling](20260930-144720_smooth-scrolling.md) design doc.

- **The Windows reader freeze.** The engine's reader thread filled a 1 MB staging buffer and waited for room, while the side that consumed it was told there was data only as a side effect of writing into that same buffer. Once full, nothing was left to tell anyone, and both ends waited forever at no CPU. Any large burst of output could hang the window. The fix has the reader announce data itself. It went upstream as alacritty/alacritty#9026 and was closed unmerged.

- **Nine combining marks per cell.** Upstream's own fix, carried until a release has it.

- **The PTY hang-up poll.** On Linux, a program that closes its terminal and keeps running spun the reader thread at a whole core. The PTY is now left out of the poll for a tenth of a second at a time, after reading what came before the hang-up.

- **Titles, handles and paths.** A title is cut to 2 KiB, so the title stack cannot be made to take gigabytes. On Windows a pane gives back its process, thread and pipe handles when it closes. A program path with a space is quoted, so a planted program earlier in that path cannot run in its place.

### The other patched crates

- **`x11-clipboard`** on `keep-value-on-clear-0.9.3`. The published crate drops the copied text on any SelectionClear, without checking when that clear was made. A clear left over from an earlier hand-over can arrive after the next copy has already taken the selection back, and wipe the text that copy just stored. The selection then stays ours with nothing behind it, and a program asking to paste gets no reply. The branch keeps the value. It is never served while another program owns the selection, and the next copy overwrites it.

- **`glyphon`** on `text-srgb-blend-0.11.0`. glyphon blends glyph coverage into a linear target, which makes dark text on a light background read thin. The branch bends coverage so the finished pixel matches an sRGB blend of the text and its background, with a contrast lift ahead of that, and leaves alone a glyph lighter than the pair's midpoint. See the [Themes](20260930-150458_themes.md) design doc. `coverage-gamma-0.11.0`, the same work as an exponent, is left standing so an older lock resolves.

### Carrying a patch

- Each patched crate is a branch under `jim-collier`, named for the published release it sits on, holding that release plus our changes and a test for each. Naming the release is what lets an older lock keep resolving. Starting from the published source, not the upstream default branch, keeps the change down to what has actually been read.

- glyphon has no release tags, so its release commit is found from the version line in its history.

- A release bump moves all three crates. Each change moves onto a new branch named for the new release.

- The tests for a patched change live in the fork and run only there. The clipboard test needs an X server and the handle test needs Windows, so running them in SilkTerm's pipeline would cover only the ledger. Each backlog item that a fork test pins says so.

- Clones of the forks for working on them live in `forks/`, which the workspace excludes.

## Alternative ideas

### Rejected

- Forking the Alacritty application. Its renderer snaps to cells, and smooth scrolling is out of scope for it upstream.

- A hard fork of the engine for Windows speed, including reading and parsing on one thread. The console host sets the ceiling, and the gain was not worth owning the parser. Backlog: "Epic 1n6fydv: Reduce CPU and GPU resource usage" and "Windows: output throughput is about a seventh of Linux".

- Parsing the scroll region (DECSTBM) ourselves, beside the engine's parser. The ledger inside the engine gives the exact record instead.

- A second fork of the VT parser to read shell directory reports. Wrapping the terminal type was enough.

- Running the fork tests in SilkTerm's pipeline. Two of the three need a platform the pipeline host does not have. Backlog: "Three fixes are pinned only by tests in the patched crates, which the pipeline never runs" (2026092621021534).

### Superseded

- Pinning the released engine plus the one freeze fix. The branch now carries five changes. Backlog: "Windows: a long run of output freezes the window for good".

- Two patched crates. There are three, with glyphon.

## Research findings

- The engine's Windows freeze reproduced with no renderer, no window and no drawing, just the engine's own PTY and event loop, and stalled at the same byte. The file had been wrong since the commit that introduced it, in October 2023.

- Under the stock `x11-clipboard`, 19 of 900 rounds lost a copy. With the patch, 0 of 900.

- Copying each outgoing row for the ledger took about a third off the parse speed on the alt screen. Handing over a spare row brought it to about 5%.

- On Windows the leak was about 200 handles for every 50 panes.

- After a hang-up, the reader burned about 1930 ms of CPU every 2 s. With the poll change, about 1 ms.

## Roadmap

- A ledger entry and a slide per scroll region, for stacked tmux panes printing at once. Backlog: "With two tmux panes stacked and both printing, only one pane slides at a time" (deferred, Opened 20260911-113647).

- Drop the combining-mark change when an engine release carries it.

- Move all three patched crates at the next engine release.
