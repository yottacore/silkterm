## Summary

Settings is a pop-out window that has every setting a person is likely to change. Its tabs are in a list down the left side, or in a row across the top. SilkTerm draws it itself rather than through a toolkit. It works fully from the keyboard, and its rows are declared in a data file that's compiled into the program. Changes show live in the terminal behind it. The rules it follows for wording, colors, and layout are in `project/uiux-style-guide.md`.

## Specification

- Settings opens as its own window, centered over the terminal, and stays on top of it. While it's open, the terminal doesn't take any input.

- The tabs run down the left side: Silk, Appearance, Movement, Window, Program, Shell, and Keys. Appearance has the Themes, Background, Text, and Cursor tabs. Settings about one subject are on one tab, even when the code stores them in different places.

- A tab can have tabs instead of rows. Across the top, its sub-tabs show in a second row while it is current. Down the left side, every tab is listed and the sub-tabs are stepped in under their parent. A parent with a sub-tab open is drawn as current along with it.

- Each tab has groups, which are titled sections. Inside a group, a switch and the rows that depend on it form a sub-group, with the dependent labels stepped to the right. Rows that only count while their switch is on stay live while it's off.

- A row that can't be used right now is grayed out, and its flyover says why. A grayed row doesn't take clicks.

- A setting the program can work out for itself, such as the font family or the window size, is automatic until a value is set, per [Settings with an automatic value](20261008-180516_automatic_settings.md).

- Every row whose value isn't its default shows a revert arrow. A click on it puts the default back.

- A fraction is shown as a whole percent. A unit is shown in the label, such as px, ms, or s.

- The footer has Cancel, Apply, and OK.
	- Apply saves and applies, and the dialog stays open.
	- OK does the same and closes.
	- Cancel closes without saving, and the live preview is undone.
	- Enter is OK and Esc is Cancel, even inside a text field. While Alt is held, the buttons underline a letter, and Alt with that letter presses the button.

- The file gets only what was edited in the dialog. Settings reads the file again each time it opens, so it shows changes another SilkTerm window saved.

- If the settings file has a line that can't be read, a save is refused, and an error box says so and names the line. OK still closes. If another program seems to have the file open, the change applies for the session, nothing is written, and OK leaves the dialog open.

- The whole dialog can be driven from the keyboard.
	- Tab and Shift+Tab walk every control, then the footer buttons, and wrap. Headers and grayed rows are skipped.
	- Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+PgUp and Ctrl+PgDn change tabs. On macOS it's Command+Shift+[ and ], or Command+PgUp and PgDn. A tab with sub-tabs is walked through them, and the step after its last one goes on to the next tab.
	- Tabs don't take focus. They're clicked, or changed with those chords, and otherwise only show where you are.
	- A text box takes Ctrl+C, X, V and A, and Ctrl moves by words. On macOS it's Command for those 4, Option for words, and Command+Left and Right for either end.
	- Space toggles, and the arrow keys adjust.
	- Walking onto a text, number, or color field selects its value.
	- Ctrl+F goes to the search box, Command+F on macOS. There, Up and Down walk the list, Enter goes to the one picked, and Esc empties the box before it cancels.

- Text fields behave like text fields everywhere else. They have mouse and keyboard selection, word moves, the clipboard, and a right-click menu with Cut, Copy, Paste, Delete, and Select all.

- A color chip opens a color picker. Edits in the picker show at once, and Cancel puts the old color back.

- A search box is above the rows and never scrolls. Typing in it lists the tabs and rows that match in place of the page, and picking one goes there.

- The dialog opens at the size its content needs, capped to the screen's work area. It can be resized, and the rows scroll when they don't fit. The size is kept for the rest of the session.

- When it's reopened within a minute, the dialog comes back on the same tab and scroll position. Values are never kept.

- The dialog follows a change of display scale without losing unapplied edits.

- Opening Settings takes well under a tenth of a second after the first time.

## Goals

- Every setting a person is likely to want can be changed without editing the file.

- A person can find a setting by what it changes on screen, rather than by how it's built.

- The dialog doesn't mislead anyone. A grayed row says why, a percent means a real percent, and a row that looks editable is saved when it's edited.

- The dialog looks and behaves the same on Linux and Windows, and at any display scale.

### Non-goals

- The dialog doesn't use a native toolkit look. SilkTerm draws the chrome, and it follows the theme.

- There isn't a native file picker. Paths are typed into text fields.

- The dialog doesn't take colors from the desktop's color scheme, since there isn't a portable way to read it.

- The dialog doesn't have every setting in the file. Some are only in the config, such as `selection_pairs`.

## Design

### A window of its own

Settings and About are pop-out windows with their own GPU context and text renderer. They're siblings of the terminal window rather than parts of it. Earlier versions drew the dialog over the terminal. That dialog conflicted with the terminal's own layout, and it couldn't be moved or scaled on its own.

- On X11 the dialog is modal through a transient-for hint that's set before the window maps, and the terminal ignores input while it's open. It's kept off the taskbar and the pager too, so the 2 windows show as one entry in each. Under Compiz the terminal is also restacked under the dialog on focus, and that's applied again so it outlasts Compiz's animated settle.

- On Windows it's an owned popup rather than a child window. winit's generic parent-window option means a child window there, which is clipped inside the terminal and never gets keyboard focus. The owned popup floats above the terminal, has its own focus, stays off the taskbar, and closes with the terminal. Windows doesn't place owned popups, so the dialog is created hidden, centered, drawn for one frame, and then shown.

- On Wayland it floats as a fixed-size modal.
	- Its toplevel sets the terminal's toplevel as its parent, which winit can't do there, so the compositor keeps it above the terminal. The compositor decides whether the 2 share one taskbar and alt+tab entry. `cicd/tests/dlgwl/run.bash` checks this.

- The dialog uses the platform's modern graphics backend rather than GL, so it doesn't clash with the terminal window's GL context.

### The GPU context is built once and kept

A dialog can't borrow the terminal's GPU context, so each one used to build a whole instance, adapter, and device on the click, and again on every reopen. That took 310 ms from keypress to a usable dialog, of which 230 ms was the GPU context. Parsing the dialog's declarations took about 1 ms.

Now one context is built on a worker thread after the terminal is shown, and kept for the life of the process. Every dialog uses it. Opening Settings takes about 86 ms, of which about 50 ms is per-window setup and about 20 ms is per-dialog font setup. The kept context costs about 52 MiB. It later measured about 200 MiB of graphics memory, per [Reducing resources](20261004-182255_reduce-resources.md#measure-first). A memory hint on every device brought that to about 21 MiB on 2026-10-04, per [The memory hint](20261004-182255_reduce-resources.md#the-memory-hint). Keeping it also avoided a driver leak of 2 file descriptors per Vulkan instance, which had stopped Settings from opening after a few times.

### Declarations in `settings_ui.shcl`

The dialog's rows are declared in `settings_ui.shcl`, which is compiled in. The file lists which rows exist, their order, the heading and tab each one is under, the setting behind each row, the graying rules, and all of the layout's measurements. `settings_ui.rs` and the files under `settings_ui/` only have behavior, which is how a value is read, written, and formatted.

- A row's name is the setting it edits. A heading starts a group and names its tab, by path where the tab is under another.

- A test fails if a row names a setting the code doesn't know, or leaves one out. That test is the only check that catches a row that's missing altogether.

- Another test drives every row through a save and a relaunch. A row whose setting is never written would otherwise change the session and be gone at the next launch, without anything to show it.

- A heading whose label is its own tab's title doesn't take any space and isn't drawn, since the tab strip already shows it. It still has to be declared, because a heading is what assigns the rows under it to a tab.

### Tabs across the top or down the side

- Where the tabs go is declared once, as `tabs_side: top` or `left`, since it's the program's choice rather than the user's. SilkTerm lists them down the left, with Appearance over Themes, Background, Text, and Cursor. The code behind the dialog supports either, so a program with few tabs can keep them across the top.

- `tabs:` lists paths, `Appearance/Text` being Text under Appearance. A tab with tabs under it doesn't have any rows of its own, so there's always one sub-tab showing while it's current. A click on it opens its first sub-tab, unless the current tab is already under it. A click on Appearance from Silk opens Themes. From Cursor it doesn't change anything, since Appearance is already drawn as current there. That's the same as a click on the current tab. A heading names its tab by that path. Any depth is allowed, though past 2 levels it's poor design rather than a limit of the code.

- Across the top, the strip gains a row for each level under the current tab, and only the current tab's sub-tabs are shown. The strip's height goes by the tab, so the dialog's natural height is the tallest of strip plus rows over the tabs, rather than the tallest rows under one strip.

- Down the left, the same gutter is a list that's the panel's height, with every tab in it. Each entry is as wide as the list, and a sub-tab is stepped in by `tab_indent` per level. A list that's taller than the panel scrolls only far enough to keep the current tab in view, as the top strip does sideways.

- In both, the current tab and every tab it's under are drawn as current. That way a sub-tab shows which parent it belongs to, and a parent shows that something under it is open.

- The tab chords walk the leaves in strip order. That one rule steps through a tab's sub-tabs and on to the next tab after the last of them. It applies to Ctrl+Tab, Ctrl+PgUp and PgDn, the macOS Command chords, and the Window menu's rows alike, since all of them call the same 2 functions.

- Tabs are never focus stops, and a click on one doesn't leave anything focused. They're chrome that shows where you are.

### Groups, sub-groups and units

- A group is a titled section with a rule under it and clear space above.

- A sub-group doesn't have a title of its own. It's a control followed by the controls that depend on it. Their labels step right, so the run looks like it belongs to the leader. Sub-groups are for a master switch and the things it controls. Every effect has one. That's transparency, wallpaper, contrast mask, text scrim, scrollbar, and smooth scrolling. The text outline doesn't have a switch, since its 0 means off.

- Only labels move. Every control stays in the one column it shares with every other row, because people scan a settings list down that column. A control that moved with its label would break that.

- A sub-group is read off the indentation in the declarations rather than declared a second time, so the leader and its members can't disagree about who belongs to what.

- A fraction that's stored as a decimal is shown as a whole percent. People don't think in 0.35, and the file has a different audience from the dialog. The two directions are exact inverses, so reverting a row gives back its own default rather than a hair off it.

- The unit is part of the label, and the help line doesn't repeat it.

- A `beside` row shares the line above it, and the control column is split in half. One revert arrow on the first half is used for both.
	- Several `beside` rows in a row make a line of that many parts, split evenly. The Tab text switches are a line of 4.
	- A line of nothing but toggles packs at its own width instead. It starts where its first label would, each label is right before its own box, and a wider gap comes before the next label. Both gaps, and the one after a radio or pair box, grow in step with the UI line height above the 11 pt default's, and never shrink below it. The label column leaves those labels out, and the panel is kept wide enough for the packed line. The Tab text line packs this way.
	- A packed line that shares its group with other rows keeps its first label and box in their columns, so that box lines up with the boxes above it. Only the toggles after it pack. This is read off the group rather than declared, the same as a sub-group. The Silk tab's hardware check line is one.

- A checkbox and a radio box grow with the UI line height at the same rate the radio box always had, so at a large font they're the same size. Each keeps its declared size as a floor, which is why the checkbox is a little bigger at the default font and stays put until the radio box catches up with it (2026100817355493).

- A slider's number field is measured the way the labels are. Its width is the longest number any slider can show in the interface font, plus the field's padding. The candidates are either end of the range, the typed cap where a row has one, and for a decimal, the top of each band before it drops a place, since 999.9 is longer than 3600. Every slider uses one width, so they all end in one column. It never drops below the floor in the declarations, so at an ordinary font nothing moves. When the field grew with the font size instead, every field got wider at ordinary sizes too, so that was dropped (2026100816465317).

- The other columns with text in them are measured the same way, each with its declared width as the floor. They're the revert arrow's column, the Shell tab's date and Active columns, and the color picker's label column and value boxes. A measured width is rounded down to a whole DIP, so a partial pixel goes into the clear space after it. The default font's date measures 78.3 DIP against the 78 it was drawn for, and nothing at that font moves. The Shell tab's name column and the gap between its columns can't be measured ahead, since the names are the user's, so they grow with the UI line height above the default's, as a label's gap does. The picker's value boxes were sized at 3 line heights, which cut "#rrggbb" short at every size, so the picker is the one place the default font changed (2026100818102267).

### Sizes and display scaling

- Every measurement in the interface is written once, in device-independent pixels (DIP), and turned into real ones only when it is drawn. A DIP is a ninety-sixth of an inch, so a border, a gap, or a checkbox is the same physical size on any screen. The terminal grid is the only thing that's sized in real pixels, and its size follows the font.

- The place where the conversion happens is different for each surface, and that's on purpose.
	- A pop-out dialog's layout is solved end to end in DIP and converted once, where the layout meets its window. It owns its whole coordinate space, so one boundary is enough, and a stray conversion inside would scale something twice.
	- The main window's chrome is converted at each measurement instead. The menu bar, tab bar, menus, focus ring, and pane gap all share a coordinate space with the terminal grid, which is in real pixels by nature, so there is no boundary to put a conversion on.

- When a measurement is taken in real pixels, the constant beside it has to be converted, rather than the other way around. Text is measured against the font, which is real pixels by nature, and the clear space around it is written in DIP. Adding the two as they stand and dividing the sum at the dialog's boundary shrinks the constant by the scale factor. At 2x a tab's title had half its clear space and sat flush against the right edge. At every such site, the constant is converted where it's used, through one rule, so the 5 places that size the dialog's columns can't drift apart.

- Conversion rounds to whole pixels. A rule or a hairline that fell between 2 of them would come out soft. A measurement that has to be visible never rounds away to zero. That's needed for the gap of 1 pixel between panes on a screen scaled below 1x.

- A mistake in raw pixels is invisible at 1x and only shows as the scale rises, so it isn't seen on the machine it was written on. `SILK_SCALE` overrides the scale factor from the environment, so a high-DPI layout can be checked on an ordinary display.

- A dialog that's already open follows a scale change in place rather than being rebuilt. Dragging it to a monitor at another scale, or changing the desktop's scaling under it, moves only the boundary. The text is rasterized again at the new size and the chrome measured again, and the layout is already in DIP. A rebuild would have been a few lines, but it would have lost every unapplied edit the moment the window crossed a monitor edge. The size kept for the session is in DIP for the same reason.

- A scale change sets both halves of the boundary. The window toolkit keeps the logical size, so for an ordinary window the new physical size comes right after. A maximized or tiled window keeps its physical size and doesn't send anything. So the dialog is told the window's real size, and the window is asked for that size, capped to what the screen can still fit.

- About and the notice box follow a scale change too, in a different way. Neither one can be resized or has a layout to adjust, so each one keeps what it was built from and is laid out again from scratch.

### Window size and scrolling

- The dialog's natural height is its tallest tab's, not counting the Shell tab. The Shell tab gets a line per shell, so it scrolls rather than making every tab as tall as its list.

- The dialog opens at its natural size, capped by the screen's work area. That's the monitor minus the taskbar and docks, and minus the frame the window manager adds. The work area is read from the terminal's monitor, since a dialog that's created hidden hasn't been placed yet. On X11 the reported work area spans every monitor at once, so it's only used as a cap.

- On macOS the work area is the screen's visible frame, below the menu bar and clear of the Dock. There and on Windows the dialog is centered over the terminal, then moved onto the work area. Linux window managers place it themselves.

- The dialog can be resized. Rows scroll vertically only when they overflow, and a horizontal scroll bar above the footer appears when the window is narrower than its content. The tab strip and the footer buttons never scroll. Neither does the search box. The search box's band and the footer are a shade toward the gutter color, halfway from the panel's, with a 1 DIP line along the rows. They look that way on every tab, whether it scrolls or not, so going from tab to tab doesn't change anything in them. The rows have a little padding inside the scrolling part, above the first and below the last. The size snaps to the natural size when it's dragged near it, and it's kept for the session only.

- The widest label on any tab sets the panel's width for every tab. Down the left, the list adds its own width on top, set by its widest entry at its step in.

- There are 2 coordinate origins, for the window and for the content, and a control has to be drawn and hit-tested in the same one.

### Chrome

- The dialog's accents follow the theme's 2 attention colors, which are Highlight and Focus. The pressed-button fill is the highlight mixed back toward the panel, which is what makes a pressed button look pressed rather than focused. Only OK has the highlight outline. See the [Themes](20260930-150458_themes.md) design doc for the 2 colors.

- A focused field shows one outline rather than 2. The ring is drawn exactly on the box's own outline, and the box drops its own border. Where the focused thing isn't a box, such as a checkbox or a slider handle, the ring is a little outside it. A color row's ring spans the chip and the hex field.
	- A ring that takes in the labels after its boxes, as a radio group's and each half of a pair's do, is never shorter than the labels' line. At a large interface font that line is taller than the boxes (2026100817355494).

- Tabs are drawn on a recessed gutter strip, on top of the rule that closes it off. Down the side the strip is a list, and the rule is along its right side. The current tab is a lighter gray rather than an accent, since "you are here" isn't the same job as "look at this".

- Controls whose label doesn't explain them have a line of flyover help, 1 to 3 sentences long. A grayed-out control explains why it's grayed instead, since that's the more urgent question at the time. A tip is kept only if it says more than the label. The text wraps to the panel rather than being clamped to its edge. Tips wait for the pointer to rest, and are laid out by the same code as every other tip in the program. A row's tip shows over all of the row, including the label, options, and controls. Only the revert arrow has its own tip. A tip doesn't show while a dropdown list or the field menu is open, or while the dialog doesn't have the focus.

- The dialog draws in the desktop's proportional interface font, at the family's closest weight, without any synthesized bold. Everything sizes off that font, so a larger interface font makes the panel wider rather than clipping it.

- Text is centered on the glyphs rather than the line box. A field has its own height rather than the color chip's, and each control is centered in its actual row.

### Controls

- Text fields keep a horizontal offset that scrolls ahead of the caret, scroll on drag, and ease both the scroll and the caret. The caret blinks with a soft fade. A fresh click selects all on release, while a drag keeps its range. A paste is checked by the field's own validation.

- A slider has 2 focus stops, the track and then its number field. Up and Down step about a hundredth of the range, Shift about a tenth, and Left and Right do the same. Pixel sliders step in whole units. A number typed into the field is clamped. For a row without a % or a limit of its own, the number can go past the slider's end, up to a cap. The 2 idle waits have a log track (2026100812334386).

- A dropdown opens on a click, Space, or Alt+Down. Up and Down move the highlight, Enter or Space picks, Esc closes, and Left and Right step without opening. Its list is drawn in a second pass on top, so covered rows can't show through. It opens upward when it would extend past the panel.

- Buttons center their captions, fire on release, and cancel if the pointer is dragged off first.

- The revert arrow is mouse-only. It's accent-colored and clickable when a value is off its default, and dim at the default. On Apply, a reverted key is dropped from the file and the default line comes back.

- A row that depends on something outside SilkTerm, such as Transparency on the desktop compositor, has a warning mark after its label, declared with `warning:` in `settings_ui.shcl`. That text goes on the end of the row's flyover, and the mark shows that one flyover like the rest of the row. It's drawn from quads rather than a font glyph, since it isn't safe to assume any interface font has the sign.
	- A mark whose text differs on Windows takes `windows_warning:`, which the Windows build shows in place of `warning:`. Transparency uses it to add that a window in view keeps its graphics memory there.

- A row that a performance profile or a theme sets shows the preset's value. Changing it puts a `*` after the preset's name and leaves Custom as it was. See the [Automatic settings](20261008-180516_automatic_settings.md) design doc.

- A row under a switch, such as Font family under Use system font, shows the switch's value while it's on. Typing in it turns the switch off. Turning the switch on again sets the typed value aside, and off brings it back. Nothing is grayed for any of this.
	- The relations are declared on the rows in `settings_ui.shcl`, with `gate:`, `auto:`, `rule:` and `group:`, and the knobs crate works them out.

- The dialog has one open edit at a time, and 5 other fields borrow it at row numbers that no real row can have. They're the theme name prompt, the shell list's name and command fields, the color picker's value boxes, and the search box. That's how all of them get selection, word moves, the clipboard, and the eased caret without a second copy of the code.

### Search

- The search box is in a band of its own between the tabs and the rows, in window space, so it stays put when the rows scroll. Every tab's rows start under it, which makes the dialog that much taller. The band is shaded and lined off from the rows like the footer, under [Window size and scrolling](#window-size-and-scrolling).

- With text in the box, a list of matches takes the rows' place under it, and scrolls like they do. The rows don't take clicks or keys while it's up. An empty list shows one line that says so.

- A match is a tab, a heading, or a row with a label. Matches come in 3 tiers, each in the dialog's own order:
	- The label has the text in it. A whole label beats its start, which beats a word's start, which beats the middle of a word.
	- One of the row's aliases does. Aliases are declared on the row in `settings_ui.shcl` as `aliases:`, for words people search by that the label doesn't use, such as "typeface" for Family. A heading that only repeats its tab's title lends its aliases to the tab.
	- A loose match has the letters in order from the start of a word, as "lnhght" does for Line height, or a word that's one typo off, or 2 for a longer word. It needs at least 3 letters, since 2 would match half the dialog.

- Each match is shown as a path. That's the tabs it's under, its heading where that isn't the tab's title, and then its label, with ⏵ between them. When 2 rows would read the same, such as the 2 Width px rows on Movement, the row they're under is added. The alias that matched follows in parentheses. The matched text is bold, a step larger, and in the Highlight color, since it marks several things at once. The line the keyboard picks gets the current tab's lighter gray, which keeps the matched text readable on it.

- When a match is picked, by click or Enter, the dialog goes to its tab and scrolls the row a third of the way down, unless it's already in view. The keyboard focus goes to the row's first control, and the row is marked in the Highlight color, which fades out over about a second and a half. The box is emptied at the same time.

- Up and Down walk the list while the box has focus. Enter with nothing matched does nothing, and with the box empty it's OK, as everywhere else. Esc empties the box first and cancels only when it's already empty.

- When the box is empty, it's outside the Tab walk, like the tabs, so Tab from nothing still goes to a tab's first control. Ctrl+F or a click puts focus on it, and Tab from it goes on to the first control. While the list is up, the walk is the box and the footer buttons.

- The search text is the dialog's one open edit, so it gets selection, word moves adn the clipboard like any field. It's kept apart from the edit, so moving focus to the footer leaves the list up.

### The color picker

- A color chip opens a picker. It has a saturation and brightness square, a hue strip beside it, 6 value boxes, and Cancel and OK. It's a modal box, and its title is the row's label. The hex field on the row stays where it is. Typing a known hex is faster than hunting for it, and a picker is for when the value isn't known yet.

- The box stores the color as hue, saturation, and brightness rather than as 3 bytes. Dragging to the bottom of the square leaves black, which doesn't have a hue, and dragging to the left edge leaves a gray, which doesn't have a saturation. Reading the model back off the bytes each frame would reset both markers the moment the color reached an edge. The bytes are derived from the model, and the trip back is exact for every color, so nothing drifts on the way in.

- Changes go straight to the row behind the box, and Cancel puts back what the row had when it opened. So the chip, and the window under the dialog, are the preview. There isn't a second copy of the value to get out of step, and undoing is one assignment.

- The square and the strip are drawn by the renderer's own quad shader, as 2 modes of it. A gradient built from flat quads would be thousands of them for one square, and a picker isn't worth a texture upload per hue.

- The square mixes toward the hue in sRGB rather than in linear light. Every other color in the program is handed to the GPU linear, and mixing toward white there gives a square that doesn't look like a color picker, since the pale half swamps everything else. So the square's quad has its hue in sRGB, and the shader encodes the result itself. That's the one exception, and it's documented where the quad is declared.

- There are 6 value boxes. They're red, green, and blue as whole percents, then brightness, saturation, and a hex value. There isn't a hue box. The strip is the hue control, and the other 5 can already name any color between them. They use percents rather than 0 to 255, because every other fraction in the dialog is shown as a whole percent.

- The chip is a focus stop of its own, so a color row has 2 focus stops, the chip and then the hex field. Walking onto the chip doesn't open anything, and Space or Enter opens the picker. Without that, the picker would be the one thing in the dialog a keyboard couldn't reach.

- Inside the box, the arrows adjust whatever has focus. They move the square by a hundredth of its range, the strip by a hundredth of a turn, and a value box by a hundredth of its own range. That's the same step every number box in the dialog uses.

### Apply, OK and Cancel

- Every change applies live, so the terminal behind the dialog is the preview. Cancel puts the live settings back.

- Apply and OK swap the live settings whole, then write the file. The file gets only what was edited in the dialog, and the write keeps comments and every line that wasn't changed. Anything chosen for the session only, such as a wallpaper from the command line, is folded in first so it isn't saved.

- The dialog's baseline is reset after each Apply, so a second Apply of another change works.

- Apply puts the default line back only for rows still at their default.

- Settings reads the file again each time it opens. So 2 SilkTerm windows see each other's saved changes, and neither one writes back what the other didn't touch.

- If a line in the file can't be read, every save is refused, since a save would drop that line. An error box says so and names the line, which can be 1 or 2 lines off after an Apply. It's shown every time for OK or Apply, and once a session for saves that weren't asked for, such as the window size. OK still closes, so the button doesn't seem broken.

- If another program seems to have the file open, the change applies for the session and isn't written, and OK leaves the dialog open to try again. The note about it goes only to stderr. This check is Linux only.

### Reopening

When Settings is closed and reopened within a minute, it comes back on the same tab and scroll position, for any kind of close. Values are never kept. The position is clamped to the new window.

## Alternative ideas

### Unconsidered

- A visible alert around a setting that changed because of another one, such as a profile change. It would reuse Effect 1 of the GPU effects epic. Backlog: "When other settings are changed automatically based on a user action to a different setting" (Opened 20260919-154614).

- Waiting for native window controls before building some of the dialog's own. It was raised in "Settings dialog: modal, scrollable, and fully keyboard-driven".

### Rejected

- egui for the chrome. It fit cleanly on the same wgpu and winit versions, but added about 32% to the release binary, and would have needed its own theme and bundled fonts. Backlog: "Settings dialog (part 2):" (canceled 20260703-091342), and "The text and UI elements in the settings dialog are misaligned".

- Taking the dialog's colors from the desktop. There isn't a portable way to read them. Backlog: "Settings dialog: system font, background image, and system-default font and size".

- Adding 2 more colors on the Themes tab for tips. Tips take shades derived from the chrome instead, the way menu hover and borders already do.

- Rebuilding the dialog on a scale change. It's simple, but it loses unapplied edits.

- A hue value box in the color picker. The strip is the hue control.

- A preview chip in the color picker. The row's own chip, and the terminal behind, are the preview.

### Superseded

- A modal drawn over the terminal, inside its window. The pop-out window replaced it. Backlog: "Settings GUI dialog".

- Sections (Appearance, Font, Window, Scrolling, Colors) in one long list, then 5 tabs. There are 10 tabs now, with groups and sub-groups. Backlog: "Group Settings items into logical sections" and "Settings dialog: real tabs across the top".

- SilkTerm's tabs in one row across the top. They're a list down the left now, with Appearance over Themes, Background, Text, and Cursor. Backlog: "Settings: move tabs to the left, including nested tabs".

- A fixed-size dialog that couldn't be resized. It's resizable now, with scrolling both ways. Backlog: "Settings dialog: on a 1080p screen at 150% the buttons sit under the taskbar".

- Graying rows that a performance profile controls. They stay editable and switch the profile to Custom. Backlog: "Extension to the idea of "Silk: Allow 'Profile' to be selected even when 'Choose automatically' is enabled".

- Radio rows for the scrim function and falloff. They're dropdowns. Backlog: "Use dropdown list boxes for Scrim function, and Scrim falloff".

- A fixed blue for the dialog's accents. They follow the theme.

- "Highlights" as the name of the calmer attention color. It's "Highlight" now.

- The tab layouts written in "Refactor settings dialog", which put the scrolling sliders and the scrim on other tabs. They were gathered onto the Silk tab. Backlog: "Settings dialog: gather the performance-related sections onto one "Silk" tab".

## Research findings

- At 1080p and 150%, the dialog measured 831 by 1063 against a 1920 by 1008 work area, so the buttons sat under the taskbar.

- The 310 ms open time was almost all GPU context: `Instance::new` 61 ms and `request_device` 161 ms. The declarations were never the cost.

- With the old build, the chrome at 2x measured short by a fifth and an eighth. At 1x, the new build draws the same as the old one.

- NVIDIA leaked 2 file descriptors per Vulkan instance, which is what made Settings stop opening after a few times.

## Roadmap

- Show "the settings file is open in another program, not saved" inside the dialog, rather than only on stderr. Backlog: "Config file rewriting is proving problematic" (closed 20260713-142351, follow-up open).

- The 3 "Animation pauses on" checkboxes on the Cursor tab, the wallpaper "Randomize" sub-group, and the 4 wallpaper contrast and saturation rows. Each needs engine work before it can be a row. Backlog: "Settings dialog" (Opened 20260719-085918).

- Check the display-scale fixes on 2 monitors at different scales, with the dialog maximized too. Backlog: "Check the display-scale fixes on two monitors at different scales" (Opened 20260919-153000).

- The warm GPU context uses about 52 MiB for the life of the process. A middle road is to drop it when the dialog closes. That isn't settled yet.
	- As measured on 2026-10-04, it's about 200 MiB of graphics memory and 16 MiB of regular memory. See [Measure first](20261004-182255_reduce-resources.md#measure-first) in the Reducing resources design doc.

- Much of the dialog work since 20260919 has been cross-built only for Windows, and needs a look there.
