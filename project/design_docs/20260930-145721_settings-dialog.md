## Summary

Settings is a pop-out window with a row of tabs across the top, holding every setting a person is likely to change. It is drawn by SilkTerm itself rather than by a toolkit, it works fully from the keyboard, and its rows are declared in a data file compiled into the program. Changes show live in the terminal behind it. The wording, colors and layout rules it follows are in `project/uiux-style-guide.md`.

## Specification

- Settings opens as its own window, centered over the terminal, and stays on top of it. While it is open the terminal takes no input.

- The tabs are Silk, Background, Text, Cursor, Movement, Themes, Window and Shell. Settings about one subject sit on one tab, even when the code keeps them in different places.

- Each tab has groups, which are titled sections. Inside a group, a switch and the rows that depend on it form a sub-group, with the dependent labels stepped to the right. Rows that only count while their switch is on stay live while it is off.

- A row that cannot act right now is grayed out, and its flyover says why. A grayed row takes no click.

- A setting the program can work out for itself, such as the font family or the window size, is automatic until a value is set, per [Settings with an automatic value](20261008-180516_automatic_settings.md).

- Every row whose value is not its default shows a revert arrow. A click on it puts the default back.

- A fraction is shown as a whole percent. A unit is shown in the label, such as px, ms or s.

- The footer has Cancel, Apply and OK.
	- Apply saves and applies, and the dialog stays open.
	- OK does the same and closes.
	- Cancel closes without saving, and the live preview is undone.
	- Enter is OK and Esc is Cancel, even inside a text field. While Alt is held, the buttons underline a letter, and Alt with that letter presses the button.

- The file gets only what was edited in the dialog. Settings reads the file again each time it opens, so it shows changes another SilkTerm window saved.

- If the settings file has a line that cannot be read, a save is refused, and an error box says so and names the line. OK still closes. If another program seems to have the file open, the change applies for the session, nothing is written, and OK leaves the dialog open.

- The whole dialog can be driven from the keyboard.
	- Tab and Shift+Tab walk every control, then the footer buttons, and wrap. Headers and grayed rows are skipped.
	- Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+PgUp and Ctrl+PgDn change tabs. On macOS it is Command+Shift+[ and ], or Command+PgUp and PgDn.
	- A text box takes Ctrl+C, X, V and A, and Ctrl moves by words. On macOS it is Command for those four, Option for words, and Command+Left and Right for either end.
	- Space toggles, and the arrow keys adjust.
	- Walking onto a text, number or color field selects its value.

- Text fields behave like text fields everywhere else: mouse and keyboard selection, word moves, the clipboard, and a right-click menu with Cut, Copy, Paste, Delete and Select all.

- A color chip opens a color picker. Edits in the picker show at once, and Cancel puts the old color back.

- The dialog opens at the size its content needs, capped to the screen's work area. It can be resized, and the rows scroll when they do not fit. The size is kept for the rest of the session.

- Reopened within a minute, the dialog comes back on the same tab and scroll position. Values are never carried over.

- The dialog follows a change of display scale without losing unapplied edits.

- Opening Settings takes well under a tenth of a second after the first time.

## Goals

- Every setting a person is likely to want is reachable without editing the file.

- A person can find a setting by what it changes on screen, not by how it is built.

- Nothing in the dialog lies. A grayed row says why, a percent is a percent, and a row that looks editable saves when edited.

- The dialog looks and behaves the same on Linux, Windows and at any display scale.

### Non-goals

- A native toolkit look. The chrome is drawn by SilkTerm and follows the theme.

- A native file picker. Paths are typed into text fields.

- Taking colors from the desktop's color scheme. There is no portable way to read it.

- Every setting in the file. Some stay config-only, such as `selection_pairs`.

## Design

### A window of its own

Settings and About are pop-out windows with their own GPU context and text renderer, siblings of the terminal window rather than parts of it. Earlier versions drew the dialog over the terminal, which fought with the terminal's own layout and could not be moved or scaled on its own.

- On X11 the dialog is modal through a transient-for hint set before the window maps, and the terminal swallows input while it is open. Under Compiz the terminal is also restacked under the dialog on focus, and that is asserted again to outlast Compiz's animated settle.

- On Windows it is an owned popup, not a child window. winit's generic parent-window option means a child window there, which is clipped inside the terminal and never gets keyboard focus. The owned popup floats above the terminal, has its own focus, stays off the taskbar and closes with its owner. Windows gives owned popups no placement, so the dialog is created hidden, centered, drawn one frame, and then shown.

- On Wayland it floats as a fixed-size modal.

- The dialog uses the platform's modern graphics backend rather than GL, so it does not clash with the terminal window's GL context.

### The GPU context is built once and kept

A dialog cannot borrow the terminal's GPU context, so each one used to build a whole instance, adapter and device on the click, and again on every reopen. That took 310 ms from keypress to a usable dialog, of which 230 ms was the GPU context. Parsing the dialog's declarations was about 1 ms.

Now one context is built on a worker thread after the terminal is shown, and kept for the life of the process. Every dialog uses it. Opening Settings takes about 86 ms, of which about 50 ms is per-window setup and about 20 ms is per-dialog font setup. The kept context costs about 52 MiB. On b23 it later measured about 200 MiB of graphics memory, per [Reducing resources](20261004-182255_reduce-resources.md#measure-first). A memory hint on every device brought that to about 21 MiB on 2026-10-04, per [The memory hint](20261004-182255_reduce-resources.md#the-memory-hint). Keeping it also avoided a driver leak of two file descriptors per Vulkan instance, which had made Settings refuse to open after a few times.

### Declarations in `settings_ui.shcl`

The dialog's rows live in `settings_ui.shcl`, which is compiled in. It says which rows exist, their order, the heading and tab each sits under, the setting behind each row, the graying rules, and all of the layout's measurements. `settings_ui.rs` and the files under `settings_ui/` keep only behavior: how a value is read, written and formatted.

- A row's name is the setting it edits. A heading starts a group and names its tab.

- A test fails if a row names a setting the code does not know, or leaves one out. It is the only thing that catches a row that is missing altogether.

- Another test drives every row through a save and a relaunch. A row whose setting is never written would otherwise change the session and be gone at the next launch, with nothing to say so.

- A heading whose label is its own tab's title takes no space and draws nothing, since the tab strip has said it already. It still has to be declared, because a heading is what assigns the rows under it to a tab.

### Groups, sub-groups and units

- A group is a titled section with a rule under it and clear space above.

- A sub-group has no title of its own. It is a control followed by the controls that depend on it, whose labels step right so the run reads as belonging to the leader. A master switch and the things it governs is what this exists for. Every effect has one: transparency, wallpaper, contrast mask, text scrim, scrollbar and smooth scrolling. The text outline has no switch, since its 0 means off.

- Only labels move. Every control keeps the one column it shares with every other row, because a settings list is scanned down that column, and a control that wandered with its label would break it.

- A sub-group is read off the indentation in the declarations rather than declared a second time, so the leader and its members cannot disagree about who belongs to what.

- A fraction stored as a decimal is shown as a whole percent. Nobody thinks in 0.35, and the file is a different audience from the dialog. The two directions are exact inverses, so reverting a row gives back its own default rather than a hair off it.

- The unit is part of the label, and the help line does not repeat it.

- A `beside` row shares the line above it, splitting the control column in half. One revert arrow on the first half answers for both.
	- Several `beside` rows in a row make a line of that many parts, split evenly. The Tab text switches are a line of four.
	- A line of nothing but toggles packs at its own width instead. It starts where its first label would, each label sits right before its own box, and a wider gap comes before the next label. Both gaps, and the one after a radio or pair box, grow in step with the UI line height above the 11 pt default's, and never shrink below it. The label column leaves those labels out, and the panel is kept wide enough for the packed line. The Tab text line packs this way.
	- A packed line that shares its group with other rows keeps its first label and box in their columns, so that box lines up with the boxes above it. Only the toggles after it pack. This is read off the group, not declared, the same as a sub-group. The Silk tab's hardware check line is one.

- A checkbox and a radio box grow with the UI line height at one rate, the one the radio box always had, so at a large font they come out one size. Each keeps its declared size as a floor, which is why the checkbox is a little bigger at the default font and stays put until the radio box catches up with it (2026100817355493).

- A slider's number field is measured the way the labels are. Its width is the longest number any slider can show in the interface font, plus the field's padding: either end of the range, the typed cap where a row has one, and for a decimal the top of each band before it drops a place, since 999.9 is longer than 3600. One width serves every slider, so they all end in one column. It never drops below the floor in the declarations, so at an ordinary font nothing moves. Growing the field with the font size instead widened every field at ordinary sizes too, and was dropped (2026100816465317).

- The other columns that hold text are measured the same way, each with its declared width as the floor: the revert arrow's column, the Shell tab's date and Active columns, and the color picker's label column and value boxes. A measured width is rounded down to a whole DIP, so a part pixel runs into the clear space after it. The default font's date measures 78.3 DIP against the 78 it was drawn for, and nothing at that font moves. The Shell tab's name column and the gap between its columns can't be measured ahead, since the names are the user's, so they grow with the UI line height above the default's, as a label's gap does. The picker's value boxes were sized at three line heights, which cut "#rrggbb" short at every size, so the picker is the one place the default font changed (2026100818102267).

### Sizes and display scaling

- Every measurement in the interface is written once, in device-independent pixels (DIP), and turned into real ones only when it is drawn. A DIP is a ninety-sixth of an inch, so a border, a gap or a checkbox is the same physical size on any screen. The terminal grid is the only thing sized in real pixels, and that follows the font.

- Where the conversion happens differs by surface, and the difference is on purpose.
	- A pop-out dialog is solved end to end in DIP and converts once, where its layout meets its window. It owns its whole coordinate space, so one boundary is enough, and a stray conversion inside would scale something twice.
	- The main window's chrome converts at each measurement instead. The menu bar, tab bar, menus, focus ring and pane gap all share a coordinate space with the terminal grid, which is in real pixels by nature, so there is no boundary to put a conversion on.

- A measurement taken in real pixels must convert the constant beside it, not the other way round. Text is measured against the font, which is real pixels by nature, and the clear space around it is written in DIP. Adding the two as they stand and dividing the sum at the dialog's boundary shrinks the constant by the scale factor. At 2x a tab's title had half its clear space and sat flush against the right edge. Every such site converts the constant where it is used, through one rule, so the five places that size the dialog's columns cannot drift apart.

- Conversion rounds to whole pixels. A rule or a hairline that fell between two of them would come out soft. A measurement asked to be visible never rounds away, which matters for the one-pixel gap between panes on a screen scaled below 1x.

- A raw-pixel mistake is invisible at 1x and only shows as the scale rises, so nobody sees it on the machine it was written on. `SILK_SCALE` overrides the scale factor from the environment, so a high-DPI layout can be looked at on an ordinary display.

- A dialog already open follows a scale change in place rather than being rebuilt. Dragging it to a monitor at another scale, or changing the desktop's scaling under it, moves only the boundary. The text is rasterized again at the new size and the chrome measured again, and the layout is already in DIP. A rebuild would have been a few lines, but it would have lost every unapplied edit the moment the window crossed a monitor edge. The size kept for the session is in DIP for the same reason.

- A scale change sets both halves of the boundary. The window toolkit keeps the logical size, so for an ordinary window the new physical size arrives straight after. A maximized or tiled window keeps its physical size and sends nothing. So the dialog is told what the window really measures, and the window is asked for that size, capped to what the screen can still fit.

- About and the notice box follow a scale change too, by a different route. Neither can be resized or has a layout to adjust, so each keeps what it was built from and is laid out again from scratch.

### Window size and scrolling

- The dialog's natural height is its tallest tab's, leaving out the Shell tab. That tab grows a line per shell, so it scrolls rather than making every tab as tall as its list.

- The dialog opens at its natural size, capped by the screen's work area: the monitor less the taskbar and docks, less the frame the window manager adds. The work area is asked of the terminal's monitor, since a dialog created hidden has never been placed. On X11 the reported work area covers every monitor at once, so it is taken as a cap.

- On macOS the work area is the screen's visible frame, below the menu bar and clear of the Dock. There and on Windows the dialog is centered over the terminal, then moved onto the work area. Linux window managers place it themselves.

- The dialog can be resized. Rows scroll vertically only when they overflow, and a horizontal scroll bar above the footer appears when the window is narrower than its content. The tab strip and the footer buttons never scroll. The size snaps to natural when dragged near it, and is kept for the session only.

- The widest label on any tab sets the panel's width for every tab.

- There are two coordinate origins, window and content, and a control must be drawn and hit-tested in the same one.

### Chrome

- The dialog's accents follow the theme's two attention colors, Highlight and Focus. The pressed-button fill is the highlight mixed back toward the panel, which is what makes a pressed button read as pressed rather than focused. Only OK carries the highlight outline. See the [Themes](20260930-150458_themes.md) design doc for the two colors.

- A focused field shows one outline, not two. The ring sits exactly on the box's own outline, and the box stands its border down. Where the focused thing is not a box, such as a checkbox or a slider handle, the ring sits a little outside it. A color row's ring spans the chip and the hex field.
	- A ring that takes in the labels after its boxes, as a radio group's and each half of a pair's do, is never shorter than the labels' line. At a large interface font that line is taller than the boxes (2026100817355494).

- Tabs sit on a recessed gutter strip and stand on the rule that closes it off. The current tab is a lighter gray rather than an accent, since "you are here" is not the same job as "look at this".

- Controls whose label does not explain them carry a line of flyover help, one to three sentences. One that is grayed out explains why instead, that being the more urgent question at the time. A tip is kept only if it says more than the label. The text wraps to the panel rather than being clamped to its edge. Tips wait for the pointer to rest, and are laid out by the same code as every other tip in the program. A row's tip shows over all of it, label, options and controls alike, and only the revert arrow answers with its own.

- The dialog draws in the desktop's proportional interface font, at the family's closest weight, with no synthesized bold. Everything sizes off that font, so a larger interface font makes the panel wider rather than clipping it.

- Text centers on the glyphs, not the line box. A field has its own height, not the color chip's, and each control centers in its actual row.

### Controls

- Text fields keep a horizontal offset that scrolls ahead of the caret, scroll on drag, and ease both the scroll and the caret. The caret blinks with a soft fade. A fresh click selects all on release, while a drag keeps its range. A paste is checked by the field's own validation.

- A slider is two focus stops, the track and then its number field. Up and Down step about a hundredth of the range, Shift about a tenth, and Left and Right do the same. Pixel sliders step in whole units. A number typed into the field is clamped. A row with no % and no limit of its own lets it go past the slider's end, up to a cap, and the two idle waits have a log track (2026100812334386).

- A dropdown opens on a click, Space or Alt+Down. Up and Down move the highlight, Enter or Space picks, Esc closes, and Left and Right step without opening. Its list draws in a second pass on top, so covered rows cannot bleed through, and it opens upward when it would spill past the panel.

- Buttons center their captions, fire on release, and cancel if the pointer is dragged off first.

- The revert arrow is mouse-only. It is accent-colored and clickable when a value is off its default, and dim at the default. On Apply, a reverted key is dropped from the file and the default line comes back.

- A row that depends on something outside SilkTerm, such as Transparency on the desktop compositor, has a warning mark after its label, declared with `warning:` in `settings_ui.shcl`. That text goes on the end of the row's flyover, and the mark shows that one flyover like the rest of the row. It is drawn from quads rather than a font glyph, since no interface font can be relied on to have the sign.
	- A mark whose text differs on Windows takes `windows_warning:`, which the Windows build shows in place of `warning:`. Transparency uses it to add that a window in view keeps its graphics memory there.

- A row a performance profile governs shows the profile's value. Editing it moves the profile to Custom, keeps the values on screen and turns off automatic choice. Such a row has no revert arrow. See the [Performance profiles](20260930-151204_performance-profiles.md) design doc.

- An automatic setting's box shows the value in use in a lighter italic, with an "A" mark at its right end. Once set by hand the mark is an x that puts it back, and emptying the box does too. The table of automatic settings and the one function that reads them, `config::auto::value`, are in config.rs, and the lint stage refuses any other read of a stored value (`cicd/tests/autoread`).
	- A group's switch is declared with `group:` in place of `setting:`. It stores nothing, has no revert arrow, and shows a dash while its members disagree.
	- A launch takes the old follow switches (`font.use_system_family`, `font.use_system_size`, `window.remember_size`) out of a file and comments out each value one of them overrode, so the file loads what it did before.

- The dialog has one open edit at a time, and four other users borrow it at row numbers no real row can have: the theme name prompt, the shell list's name and command fields, and the color picker's value boxes. That is how all of them get selection, word moves, the clipboard and the eased caret with no second copy of the code.

### The color picker

- A color chip opens a picker: a saturation and brightness square, a hue strip beside it, six value boxes, and Cancel and OK. It is a modal box titled with the row's label. The hex field on the row stays where it is. Typing a known hex is faster than hunting for it, and a picker is for when the value is not known yet.

- The box keeps the color as hue, saturation and brightness rather than as three bytes. Dragging to the bottom of the square leaves black, which says nothing about hue, and dragging to the left edge leaves a gray, which says nothing about saturation. Reading the model back off the bytes each frame would send both markers home the moment the color reached an edge. The bytes are derived from the model, and the trip back is exact for every color, so nothing drifts on the way in.

- Changes go straight to the row behind the box, and Cancel puts back what the row had when it opened. That makes the chip, and the window under the dialog, the preview. There is no second copy of the value to get out of step, and the one thing to undo is one assignment.

- The square and the strip are drawn by the renderer's own quad shader, as two modes of it. A gradient built from flat quads would be thousands of them for one square, and a picker is not worth a texture upload per hue.

- The square mixes toward the hue in sRGB, not in linear light. Every other color in the program is handed to the GPU linear, and mixing toward white there gives a square nobody would recognize as a color picker, since the pale half swamps everything else. So the square's quad carries its hue in sRGB and the shader encodes the result itself. That is the one exception, and it is written down where the quad is declared.

- Six value boxes: red, green and blue as whole percents, then brightness, saturation and a hex value. There is no hue box. The strip is the hue control, and the other five can already name any color between them. Percents rather than 0 to 255, because every other fraction in the dialog shows as a whole percent.

- The chip is a focus stop of its own, so a color row has two: the chip, then the hex field. Walking onto the chip opens nothing, and Space or Enter opens the picker. Without that the picker would be the one thing in the dialog a keyboard could not reach.

- Inside the box, the arrows adjust whatever has focus: the square by a hundredth of its range, the strip by a hundredth of a turn, and a value box by a hundredth of its own range. That is the same step every number box in the dialog takes.

### Apply, OK and Cancel

- Every change applies live, so the terminal behind the dialog is the preview. Cancel puts the live settings back.

- Apply and OK swap the live settings whole, then write the file. The file gets only what was edited in the dialog, and the write keeps comments and every line nobody changed. Anything chosen for the session only, such as a wallpaper from the command line, is folded in first so it is not saved.

- The dialog's baseline is reset after each Apply, so a second Apply of another change works.

- Apply puts the default line back only for rows still at their default.

- Settings reads the file again each time it opens. Two windows of SilkTerm therefore see each other's saved changes, and neither writes back what the other did not touch.

- If a line in the file cannot be read, every save is refused, since a save would drop that line. An error box says so and names the line, which can be one or two off after an Apply. It is shown every time for OK or Apply, and once a session for saves nobody asked for, such as the window size. OK still closes, so the button does not seem to do nothing.

- If another program seems to hold the file open, the change applies for the session and is not written, and OK leaves the dialog open to try again. The note about it goes only to stderr. This check is Linux only.

### Reopening

Closing and reopening Settings within a minute comes back on the same tab and scroll position, for any kind of close. Values are never carried over. The position is clamped to the new window.

## Alternative ideas

### Unconsidered

- A visible alert around a setting that changed because of another one, such as a profile change. It would reuse Effect 1 of the GPU effects epic. Backlog: "When other settings are changed automatically based on a user action to a different setting" (Opened 20260919-154614).

- Waiting for native window controls before building some of the dialog's own. Raised in "Settings dialog: modal, scrollable, and fully keyboard-driven".

### Rejected

- egui for the chrome. It fit cleanly on the same wgpu and winit versions, but added about 32% to the release binary, and would have needed its own theme and bundled fonts. Backlog: "Settings dialog (part 2):" (canceled 20260703-091342), and "The text and UI elements in the settings dialog are misaligned".

- Taking the dialog's colors from the desktop. There is no portable way to read them. Backlog: "Settings dialog: system font, background image, and system-default font and size".

- Two more colors on the Themes tab for tips. Tips take shades derived from the chrome instead, the way menu hover and borders already do.

- Rebuilding the dialog on a scale change. Simple, but it loses unapplied edits.

- A hue value box in the color picker. The strip is the hue control.

- A preview chip in the color picker. The row's own chip, and the terminal behind, are the preview.

### Superseded

- A modal drawn over the terminal, inside its window. Replaced by the pop-out window. Backlog: "Settings GUI dialog".

- Sections (Appearance, Font, Window, Scrolling, Colors) in one long list, then five tabs. There are eight tabs now, with groups and sub-groups. Backlog: "Group Settings items into logical sections" and "Settings dialog: real tabs across the top".

- A fixed-size dialog that could not be resized. It is resizable now, with scrolling both ways. Backlog: "Settings dialog: on a 1080p screen at 150% the buttons sit under the taskbar".

- Graying rows a performance profile governs. They stay editable and switch the profile to Custom. Backlog: "Extension to the idea of "Silk: Allow 'Profile' to be selected even when 'Choose automatically' is enabled".

- Radio rows for the scrim function and falloff. They are dropdowns. Backlog: "Use dropdown list boxes for Scrim function, and Scrim falloff".

- A fixed blue for the dialog's accents. They follow the theme.

- "Highlights" as the name of the calmer attention color. It is "Highlight" now.

- The tab layouts written in "Refactor settings dialog", which put the scrolling sliders and the scrim on other tabs. They were gathered onto the Silk tab. Backlog: "Settings dialog: gather the performance-related sections onto one "Silk" tab".

## Research findings

- At 1080p and 150%, the dialog measured 831 by 1063 against a 1920 by 1008 work area, so the buttons sat under the taskbar.

- The 310 ms open time was almost all GPU context: `Instance::new` 61 ms and `request_device` 161 ms. The declarations were never the cost.

- Measured 2x chrome with the old build was short by a fifth and an eighth. At 1x the new render is byte-identical to the old.

- NVIDIA leaked two file descriptors per Vulkan instance, which is what made Settings stop opening after a few times.

## Roadmap

- Show "the settings file is open in another program, not saved" inside the dialog, not only on stderr. Backlog: "Config file rewriting is proving problematic" (closed 20260713-142351, follow-up open).

- The three "Animation pauses on" checkboxes on the Cursor tab, the wallpaper "Randomize" sub-group, and the four wallpaper contrast and saturation rows. Each needs engine work before it is a row. Backlog: "Settings dialog" (Opened 20260719-085918).

- Check the display-scale fixes on two monitors at different scales, with the dialog maximized too. Backlog: "Check the display-scale fixes on two monitors at different scales" (Opened 20260919-153000).

- The warm GPU context keeps about 52 MiB for the life of the process. A middle road is to drop it when the dialog closes. Not settled.
	- Measured on b23 on 2026-10-04, it is about 200 MiB of graphics memory and 16 MiB of regular memory. See [Measure first](20261004-182255_reduce-resources.md#measure-first) in the Reducing resources design doc.

- Much of the dialog work since 20260919 has been cross-built only for Windows, and needs a look there.
