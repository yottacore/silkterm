## Summary

A theme is a named set of colors with a dark and a light variant. SilkTerm comes with four, and any of them can be edited and saved under a new name. Around the themes sit the rules that keep text readable whatever colors a program asks for: a minimum contrast floor, a correction that keeps dark text on a light background from looking thin, and a cursor plate the character under it can still be read on.

## Specification

- Four built-in themes, each with a dark and a light variant: SilkTerm, Matrix, Retro Amber and Pastel. SilkTerm is the default.

- Mode is Dark, Light or System. System follows the desktop, and falls back to dark where the desktop says nothing, as X11 does.

- Dark mode means a dark background and light text, for the terminal and the dialogs alike. Light mode is the reverse. A dialog's background is a different shade from the terminal's.

- Twelve colors can be edited on the Themes tab, each with one job. A changed color overrides the theme until it is saved into a theme or the theme is picked again.

- While any color is changed from its theme, the Theme box reads `[unsaved]`.

- Picking a theme takes all its colors. Edits made to the theme being left are dropped.

- Save as stores the current colors as a new theme, whole. A saved theme can be renamed or deleted. A built-in cannot be.

- A saved theme may take a built-in's name and stand in for it. Deleting it brings the built-in back.

- A theme carries two attention colors, Highlight and Focus, and they must stay clearly apart. Highlight marks the live pane, slider handles, revert arrows and the default button. Focus marks the one control the keyboard is on.

- Menus and dialogs share the same neutral colors in every theme by default. They can be overridden.

- No text may come closer to its cell's background than the minimum contrast floor, 45% by default and a tenth more in a light theme. Text under the floor is moved lighter or darker, keeping its hue. Text set to exactly the background color stays hidden.

- In a light theme, dark text is corrected so it looks as heavy as the same font does in a dark theme.

- Reverse-video text is drawn bold, since it otherwise looks thinner.

- The character under a block cursor must clear the contrast floor against the cursor's plate, in every built-in theme and mode.

- The text and cursor colors can come from the wallpaper instead. See the [Wallpaper](20260930-150052_wallpaper.md) design doc.

## Goals

- Every built-in theme is readable in both modes, with no edits.

- Any program's colors stay readable, including a program that assumed the wrong background.

- A theme can be edited, saved, handed to someone else and brought back without any stale state.

- Light mode is as comfortable to read as dark mode.

### Non-goals

- Guaranteeing contrast against the wallpaper pixel by pixel. The floor is measured against the cell's color, and the scrim covers the rest.

- Following the desktop's accent colors. There is no portable way to read them.

## Design

### Palettes, themes and overrides

- A palette is a background, a foreground, a cursor, the two attention colors, the gutter, the scrollbar pair, the menu and dialog colors, and the sixteen ANSI colors. A theme is a dark palette and a light palette. The theme and mode settings pick the active palette, and each color setting overrides one color.

- A color override that is not the theme's own survives the desktop switching between dark and light.
	- Each color is an automatic setting now. One set by hand stays put, even at the theme's own value, and one left automatic follows the theme.

- Every theme carries menu and dialog colors, with the same neutral defaults shared across all of them. Menu hover, border and separator shades follow the menu color, so a custom menu color stays coherent.

- Flyover tips fill with a shade derived from the menu color rather than a color of their own. See the [Settings dialog](20260930-145721_settings-dialog.md) design doc.

### Attention colors

A theme carries two attention colors rather than one, because they answer different questions. **Highlight** marks several things at once: the live pane's ring, slider handles, revert arrows, the default button. It therefore stays calm enough to appear many times on a screen. **Focus** marks the single control the keyboard is on, so it is the more vivid of the pair and sits well away from its partner in hue. Every theme keeps its two about 120 degrees apart, because a theme that let them come together would draw "look at this" and "you are here" in the same color.

The dialog's own accents follow the theme. They used to be a fixed blue while the theme's attention color was something else, so the panel could not agree with the terminal it belonged to. The pressed-button fill is the highlight mixed back toward the panel, which is what makes a pressed button read as pressed rather than as the focused one.

### Saved themes

- A theme the user saves is stored **whole**: both variants, the palette colors and the sixteen ANSI colors, rather than as a base theme plus the differences.
	- Saving, renaming and deleting all become one operation on one config subtree.
	- A stale color cannot survive under a name that no longer sets it.
	- A saved theme is self-contained enough to hand to someone else.

- What identifies a saved theme in the file is a slug that never changes, with the display name stored beside it. A rename therefore rewrites one line instead of moving a subtree, and the `theme` setting keeps a name a person would recognize. A theme can be renamed to its own name or a change of case. Another theme's name is refused.

- **Nothing records "this theme has unsaved changes".** A per-color override that disagrees with the theme is that record, and it already lives in the config file. So the Save button is right after a restart, with no flag to keep in step. Saving folds the overrides into the theme and drops them, which is also what makes the button go quiet again.

- While an override is in place the Theme dropdown says `[unsaved]` rather than naming a palette the colors have moved away from. It is display only, worked out from the same test the Save button uses, so nothing extra is stored. The list underneath is unchanged and still highlights the theme the edits started from. That is both how to see what they started from and how to throw them away: pick it again and its colors come back.

- A saved theme may take a built-in's name and stand in for it. That gives "customize a built-in" an obvious home, and deleting the saved copy puts the built-in back rather than leaving the name pointing at nothing. Built-ins themselves cannot be renamed or deleted.

- Picking a theme takes on its colors wholesale rather than keeping the previous theme's edits on top. A picker that visibly changed nothing on every color that had been edited would read as broken, and those edits belonged to the theme being left behind.

### The built-in themes

- **SilkTerm**: mint text (#88eecc) on black, with a deep violet cursor (#8a3fa4). The light variant is a near-black ink blue (#080d23) on warm white.

- **Matrix**: green on black, ANSI colors included.

- **Retro Amber**: amber on black.

- **Pastel**: soft cream text on a dark gray with a faint blue tint, the complement of the text. The light variant turns it round, the same hues deepened on cream paper. Every ANSI color is at the same low saturation, with the bright row a step lighter rather than a step more vivid, so no one color jumps out of the set.

A light theme's colors are deeper than its dark twin's are bright, but not by as much. Its ANSI colors sit 0.52 to 0.54 Oklab L under the paper on average, each one just past the light contrast floor, where a dark theme's sit 0.60 to 0.77 over black. Much deeper and a yellow or a cyan has no color left to show. They used to average 0.36 to 0.47, so the contrast floor was holding most of them up. Then they went to 0.57, which looked too dark once light text was drawn heavier, so they were eased about a third of the way back. Chroma was kept or raised when they were darkened, so each reads as a more saturated color rather than a muddier one. The two monochrome themes moved their whole set down instead, since the spread between their colors is all that tells them apart. The cost is that the same colors used as a cell background are now dark, so the floor turns the text on them light.

Tests keep the built-ins to one structure: shared chrome, a recessed gutter, the two attention colors about 120 degrees apart, the foreground clearing the contrast floor, ANSI black not clearing it, the cursor plate carrying its text, and a light theme's colors standing well off the paper while still reading as colors. A new theme is picked against those, not by eye alone.

### Minimum contrast

Programs pick text colors for a terminal they cannot see. One that assumes a light background writes near-black text, and on a dark one it disappears. So a floor is kept on how close text may come to the color behind it, and anything under it is moved away: lighter on a dark background, darker on a light one.

The comparison is against the cell's own background color, not against what a pixel behind the glyph actually shows. Per-pixel would mean the wallpaper, the blur, the scrim and the cell color all at once, in the shader, and it would give one word two colors across a gradient. The cell color is also the right answer in practice. A cell with its own background paints it solid, and one on the default background gets a scrim halo of exactly that color, with the wallpaper already pulled most of the way toward it.

Lightness is measured in Oklab rather than as a WCAG ratio. That ratio's constant term swamps the dark end, so two near-blacks score respectably while being invisible, which is the whole case this is for. The move changes Oklab L alone and leaves a and b, so hue and saturation survive and colors stay told apart: a lifted navy is still navy. It goes to whichever side the text is already on, unless that side has no room left before white or black, in which case it goes the other way. Pale text on a merely light background is the case that needs the flip.

The default floor is 45%, which puts previously invisible text at roughly 2.8:1 against a black background. Lower settings measure out as doing nothing visible at all. Two things are exempt on purpose. Text set to exactly its background color is left hidden, since that is how the hidden attribute works and how a program conceals a password. And ANSI black on a dark background is not exempt, even though it is invisible by definition. A program using it as a foreground has made the mistake this setting is for.

Every built-in theme's own foreground clears the floor on its own, which is checked at build time. A theme whose body text needed lifting would mean the floor was repainting the thing it is measured against.

### The cursor plate

The block cursor is a second background. It is drawn as a plate at 55% under the glyph, and the glyph keeps its own color, so the text on it has to clear the same floor against the plate as blended over the theme's background. That is checked for every built-in theme and mode the same way. A cursor at the text's own brightness fails it outright, which is what the monochrome themes first shipped with. In a light theme the rule also sets how dark the text has to be. The plate sits between the text and the background, and a paler foreground leaves no room for one that both shows as a block and carries the text.

Over a light background the plate is drawn at 80% instead. A linear-light blend barely moves a light ground, so at 55% even a black cursor could not take the plate much more than 0.2 Oklab L off the paper. The stronger alpha goes only as far as the text on the plate still clears the floor, so a saved theme or an overridden cursor picked for the old plate keeps about the plate it had. The shipped light themes' text was darkened to make the room. Their plates now sit 0.25 to 0.28 off the background, against 0.20 to 0.42 in dark mode. Colors taken from the wallpaper follow the same rule, since the derived text is never paler than the theme's.

A cursor color that is the foreground's channels in another order is an exact color triad, with the same brightness. Text on such a plate cannot be read, whatever the hues. That is why the SilkTerm cursor is a deep violet, not the gold of that triad.

### Dark text on a light background

The color pipeline works in linear light, and glyph coverage is blended there too. A pixel the rasterizer says is half covered comes out at about three quarters brightness either way round. On a dark background that is a strong edge. On a light one it is barely a quarter of the ink the eye expects, so the thin parts of every stroke fade and a light theme reads a weight lighter than the same font in a dark one. Bold survives because most of its pixels are fully covered.

What the text should look like is settled first. Almost every other program blends text in sRGB, and that is the weight a font is drawn and hinted for, so the target is the pixel an sRGB blend of the pair would have produced.

The fix reaches it without blending there. glyphon's fragment shader is given the text color, its background and an amount, all in the params uniform, and it bends coverage so the finished pixel comes out on that target: blend the pair in sRGB at the reported coverage, decode, and read off how far between the two the answer sits. That fraction is the alpha. The output is still linear and the surface is still encoded exactly once, which is what the color pipeline contract is about. The rejected alternative was a second encode of the output inside the text pass, not arithmetic that reads the sRGB curve. The change is carried on the glyphon fork (see the [terminal engine](20260930-151451_alacritty-fork.md) design doc for how forks are carried).

An sRGB blend is the weight the font was drawn for, but it still leaves a light theme looking thinner than a dark one, since dark mode's linear blend gives light text more than that. So ahead of the match the shader lifts the partly covered pixels with the curve DirectWrite calls enhanced contrast, `c * (k + 1) / (c * k + 1)`, the way desktop text renderers darken dark-on-light text. The ends stay put, so a letter keeps its shape and nothing moves. `k` is `DARK_ON_LIGHT_CONTRAST`, 2.2, set by measuring the same text in both modes of every built-in theme.

`text.dark_on_light` says how much of the correction to apply, 1.0 by default, and it is applied only where the text is darker than the background behind it. Light on dark is already heavy enough, and correcting that side would thin it. The comparison is Oklab lightness, the same measure minimum contrast uses.

The setting runs to 2.0 rather than stopping at the blend. Everything up to 1.0 is a correction, and 1.0 is the whole of it. Above that is taste, and it is there because how heavy text ought to look is partly the display and the font. It fills the counters of small letters if pushed, which the config comment says.

One alpha has to serve all three channels, so the pair reaches the shader as sRGB grays of its own brightness. A glyph in some other color, such as an ANSI red, takes the same curve, which measures up to about 20 levels off on its partly covered pixels, always toward more ink. Correcting per glyph would mean encoding each glyph color in the shader for a difference smaller than the one being fixed.

The pair is chosen once per render pass, not per glyph, because one pass draws the whole window and a uniform is what the shader can read. Each glyph then only says which side it is on: one lighter than the gray halfway between the pair is left alone. So the menu and tab labels, which stay on dark chrome in both modes, draw the same in both, and so does light text on a dark cell in a light theme. Before that check they were corrected along with everything else, in the wrong direction, which was accepted while the correction was mild. The Settings dialog is a separate context and works this out from its own panel colors.

### Reverse video

Reverse video, dark on light, looks thinner than the same weight light on dark, in every terminal. The scrim only helps light-on-dark text. So `embolden_inverse`, on by default, draws reverse-video runs bold.

### Color pipeline

Every color is handed to the GPU in linear light, and the surface is sRGB, so the clear color is linear too. The selection's offscreen buffer is left unencoded, and the final copy does the one sRGB encode. The color picker's square is the one exception, described in the [Settings dialog](20260930-145721_settings-dialog.md) design doc.

## Alternative ideas

### Unconsidered

- An "Old CRT mode" that lays effects over the theme without changing it: scan lines, mono white, green or amber, CGA or EGA colors, tube bulge, vignette, and a choice of period monitor bezels. Backlog: ""Old CRT mode" (boolean that might overrides - but not change - some theme settings)".

### Rejected

- Solarized as the fourth theme. Pastel was chosen. Backlog: "Themes: a fourth built-in theme".

- A WCAG contrast ratio for the floor. It rates two near-blacks as readable.

- Measuring contrast per pixel against the wallpaper. One word would get two colors across a gradient.

- Blending text in sRGB, a second encode inside the text pass. It breaks the one-encode rule.

- A separate text pass for the chrome in light mode. A second renderer and atlas for a few hundred pixels.

- Two more tip colors on the Themes tab. Tips use derived shades.

### Superseded

- A cursor that was the foreground's channels in another order (#eecc88 on #88eecc). The two had the same brightness, so text under the cursor could not be read. Backlog: "New default color scheme" and "Bug: Text sitting under the cursor is hard to read".

- Earlier defaults: foreground #88ffee with cursor #ff88aa, and before that a gray and a steel blue. Backlog: "Cursor settings: size as two percentages, plus an animation style".

- A coverage exponent for dark text on light (`text.dark_on_light_gamma`). No single exponent fits the curve an sRGB blend needs. The sRGB-match correction replaced it. Backlog: "In light mode the same system fonts read too thin".

- Three built-in themes with "dark text on light gray" light variants. There are four now, and the light text was darkened to make room for the cursor plate. Backlog: "Themes: a set of themes, each with a dark and a light variant".

- A fixed 55% cursor plate in both modes. Light mode draws it at 80%. Backlog: "Two more settings of the same class as the light mode calibration".

- "Highlights" and "Focus ring" as the names of the attention colors. They are Highlight and Focus.

## Research findings

- An sRGB blend needs roughly 0.53 at a quarter coverage, 0.35 at a half and 0.18 at three quarters. The exponent that first shipped was about 20 sRGB levels light on a three-quarter covered pixel.

- Ink on partly covered pixels went from 40.3% to 51.5% with the correction on the shipped light theme.

- With the sRGB match alone, a screen of text in a light theme put down about 80% of the ink, in sRGB levels, that the same text did in that theme's dark mode. With the contrast lift at 2.2 it was 100% to 104% in all four themes, and the count of solid pixels matched dark mode's too. Pushing `text.dark_on_light` to 2.0 instead reached the same ink by turning more than twice as many pixels solid, which is what fills counters.

- Light text sits at Oklab 0.32 to 0.37 and the light backgrounds at 0.94 to 0.97, so a plate at 55% could only get 0.12 to 0.20 away from the background. Dark mode gets 0.20 to 0.42.

- The default foreground and the old gold cursor stood at under 2:1. The violet cursor is close to 6:1.

- A floor under 45% measured as doing nothing visible.

## Roadmap

- The per-theme gaps for the light cursor plate, 0.28 for SilkTerm down to 0.25 for Pastel, were a best guess and want a look on screen. Backlog: "Two more settings of the same class as the light mode calibration".

- Flip the scrim's color under text lifted for contrast, instead of moving the text. See the [Text scrim](20260930-145304_scrim.md) design doc.

- Faux-bold, by stroke dilation, if bold reverse video reads as too subtle.
