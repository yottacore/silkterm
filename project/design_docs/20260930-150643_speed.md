## Summary

Smooth scrolling is no use if the terminal falls behind the moment something dumps a lot of text. So SilkTerm is built to swallow output as fast as a plain terminal does, to answer a keystroke quickly, and to do as little work per frame as it can. Speed is measured against other terminals with a benchmark anyone can run, and the results are published in the README.

## Specification

- Heavy output must never stall the window or freeze a pane. The picture may lag the output by the scroll ease's braking distance, never more.

- Reading the program's output always comes first. Drawing waits for it, and never the other way round.

- A frame whose text did not change does no text work at all.

- Only rows whose content changed are shaped again.

- Speed is measured as throughput under a flood: how fast the terminal swallows output and keeps up. It is not a measure of how fast glyphs are drawn.

- Every published speed figure comes from one machine and one rig, at a 160 by 42 grid. There are no Windows speed rows, since on Windows the console host sets the pace, not the terminal.

- The release build favors size where speed is the same. It is never packed or compressed, since packers trip antivirus software.

- `SILK_PERF=1` reports where a burst of output went. `SILK_LATENCY=1` times each keystroke in three parts. Both cost nothing when off.

## Goals

- Throughput at least as good as the plain, fast terminals, with every effect on.

- A keystroke echoed on screen as soon as the shell answers.

- An idle window that costs nothing measurable. See the Releasing resources design doc.

- Numbers that can be checked. Every claim about speed comes from a measurement, with a control.

### Non-goals

- Beating the console host on Windows. Its delivery rate is fixed, and every Windows terminal sits at or under it.

- Winning on plain ASCII alone. The score leans toward ASCII but counts every width class.

## Design

### Output reaches the window as one notice at a time

- A pane's reader finishes a read cycle roughly every 900 bytes when output is pouring in, and each cycle used to become its own window event. On 32 MiB of output that is about 20,000 events. The window now takes delivery of at most one at a time. The notice carries nothing, so the window reads the grid as it stands whenever it gets round to one, and a queue of twenty identical notices only ever produced twenty identical reads.

- Measured on the Windows box, the folding costs nothing and saves a great deal. Throughput is unchanged, 11.8 against 11.7 MB/s over four alternating pairs, while the process burns a third less CPU and the window thread less than half. The 2.5 seconds that used to go into the operating system's message queue was more than parsing and drawing put together.

- The notice is re-armed before the window acts on it, so a read cycle that arrives mid-handling posts a fresh one rather than being dropped. That ordering is the whole safety argument, and it is what a unit test pins.

### Sharing the terminal with the reader

The reader thread keeps the terminal locked across a whole read cycle, so the renderer cannot simply take it every frame without stalling. It also cannot merely try and give up. The reader takes it back at once, and an impatient try can lose forever, which showed up as a pane frozen for seconds during heavy output: on a large `cat`, 98% of frames showed a stale picture.

The rule is to try first, and after two frames in a row of getting nowhere, wait properly. Waiting takes a numbered ticket, which puts the renderer at the end of the current read cycle and makes the reader queue behind it. So the wait is bounded, under 5 ms, where the polite try was not. The worst stale run went from 2083 ms to 52 ms at the same frame rate. This only comes into play when something is actually contending.

### Less work per frame

- A per-frame signature covers everything that feeds the prepared text. When it repeats, the text prepare passes and the atlas trim are skipped. Anything the signature misses costs an extra prepare, never a stale frame.

- The same signature gates the scrim's color map, coverage pass and blur, so a cursor-only frame reuses the halo.

- The text is handed to the renderer row by row, not as one joined blob, so each row is compared first and only rows that really changed are shaped again. This catches a line rewritten with identical content, which shells do all the time. The engine's own damage report is not used. It would miss that case, and separate damage bookkeeping could drift out of step with our rendering. Reading the whole grid is under 2% of a frame, so skipping unchanged rows at read time was not worth the risk.

- Each fallback glyph is shaped once per pane, keyed by character, bold and italic, and tinted per cell.

- sRGB to linear is a 256-entry table rather than three `powf` calls per colored cell.

- Per-row strings and each pane's background quad list are recycled across frames. The scrim's de-bold pass does not clone rows, and the scrolled-off strip moves rows out of the old snapshot rather than cloning them.

- Attribute runs, scroll easing and text areas each read one settings snapshot per frame. The tab title probe runs at 4 Hz, not per frame.

- On the GL path, the framebuffer and offscreen views are made once per resize, not twice per frame.

- An open context menu does not shape its labels again on every cursor blink, and shaped menu and tab text is cached.

- Mouse motion reported to a program does not cause a redraw.

### Windows delivery

On Windows a terminal never receives its output directly. The console host relays it over a pipe, and that pipe sets the pace.

- The console host's delivery rate is about 22 MB/s, and it is fixed. Pipe buffers from the default to 16 MB, read sizes from 64 KB to 1 MB, every pseudoconsole mode flag, and Microsoft's newer redistributable host all sit inside the noise.

- A consumer that reads the bytes and throws them away gets the same figure as the terminal on every width class. So a Windows figure measures the transport, and Windows Terminal reads fastest only because it hosts the console itself.

- What is left is about a second per 32 MiB: half a second of parsing, and the engine's Windows pipe plumbing, which delivers about 17 MB/s where a plain blocking read gets 22. Reading and parsing on one thread would beat the engine's two threads by half a second, which is the direction if this is ever picked up again.

- The engine's Windows reader once froze the window for good under a long run of output. It told the main loop "there is data" only as a side effect of filling a 1 MB buffer, so once the buffer was full the notice could never come. The fix, having the reading thread announce data itself, is carried in the engine fork and was offered upstream. See the Alacritty design doc.

### The benchmark

- `utility/update-showdown.py` runs on any terminal on any OS and needs only Python 3.

- It feeds repeatable, byte-identical streams of one character width at a time: plain ASCII, then 2-, 3- and 4-byte characters, then a mix with color and attribute changes. Two terminals are always compared on the same work.

- Each run is timed to a reply the terminal can only send once it has consumed the stream. Timing a plain write would measure the pipe, and a terminal that reads greedily would look infinitely fast.

- ASCII is measured four times as often as the wide classes, and 2-byte twice, so the score leans the way real output does. The score counts cells per second, not bytes, because bytes flatter whichever class is widest.

- Many runs per class are averaged and the spread reported, so a result carries its own confidence. History is kept per terminal name and version.

- Only a full, unscaled run at 160 by 42 writes the README table. Each terminal gets its own home, config and data folders and its own session bus, so no terminal inherits another's state.

- The rig runs under a headless Wayland compositor on a discrete GPU. XTerm draws only on X11, so its row comes from a private X server. A second rig measures install size and memory at a smaller grid, with the graphics driver split out.

- The "+candy" row runs SilkTerm with its shipped settings and the automatic performance profile pinned off.

- The rig notes and measurements are in `utility/include/showdown-readme.md`.

### Diagnostics

- `SILK_PERF=1` reports where a burst of output went: notices, loop passes, frames, the time inside each part of a frame, and the window thread's CPU against the whole process. The last one is what stops a wrong answer, since a busy window and a busy process are different problems.

- `SILK_LATENCY=1` times every keystroke in three legs: getting the key to the shell, the shell answering, and putting the answer on screen. It prints one line per keystroke, then a median, a p95 and a worst case. Only the first and third legs are SilkTerm's, and splitting them is the point. It cannot see anything after the frame is handed over, so a figure is a floor, and it belongs at a settled prompt.

- The profiler is a dev-only Cargo feature with its own build profile, run by the pipeline.

### Build settings

- The release build uses `opt-level = "s"`, fat LTO, one codegen unit, `panic = "abort"` and stripped symbols. "s" matches "3" on throughput and is 22% smaller. "z" halves throughput.

- No UPX or other packer. Packers trip antivirus heuristics.

## Alternative ideas

### Rejected

- Forking the engine for Windows speed. The console host is the ceiling, and most of what is left is in the engine's pipe plumbing. Backlog: "Windows: output throughput is about a seventh of Linux".

- A bundled newer ConPTY. It did not fix the freeze, and it asks the terminal what it is at startup and waits several seconds for a slow answer. Backlog: "Windows: try a bundled newer ConPTY to see if it fixes the freeze above".

- Batching fallback glyphs. A screen of them is cheaper than ordinary text, and assembling their areas is 1.6% of a frame. Batching would mean re-owning the glyph rasterizing that took several rounds to get right. Backlog: "Epic 1n6fydv: Reduce CPU and GPU resource usage", item 3.2.

- Using the engine's damage report to skip reading unchanged rows. The whole read is under 2% of a frame.

- `opt-level = "z"`. It halves throughput.

- Windows speed rows in the README, and a correction factor for them. Terminals that run on both platforms disagree about the ratio by more than 2x. Backlog: "Terminal throughput benchmark: the Windows speed rows".

- MobaXterm and PuTTY rows. MobaXterm's shell gives no Windows program a tty, and PuTTY has no local shell. Backlog: "Terminal throughput benchmark: MobaXterm and PuTTY rows".

### Superseded

- `opt-level = 3`. It is "s" now. Backlog: "Optimize compiled binaries to balance executable size and speed".

- Only ever trying for the terminal lock. It could lose forever.

- One window event per read cycle.

## Research findings

- On 32 MiB of output, about 20,000 notices cost 2.5 s of the window thread, against 0.5 s of parsing, 0.03 s of text layout and 0.2 s of real work.

- A keystroke that marks the window dirty lets the shell's reply arrive while that frame is still being drawn, which puts a whole frame in the middle latency leg. On a slow renderer that doubles the total.

- A screen filled with fallback symbols costs 10.9% of a core, against 24.7% for ordinary text.

- Shaping rows separately took a full screen with one line updating from 29.2% of a core to 24.7%, and all-new content every frame from 74.9% to 69.6%.

- Shaping each fallback glyph once took `fill_glyph` from about 16% of CPU to 0.2%.

- The shell directory tap costs 47 ms per 32 MiB, about 714 MB/s.

- On Windows, 32 MiB takes 1.45 s read and thrown away, 1.94 s read and parsed on one thread, 2.45 s through the engine's plumbing with no window, and about 2.5 s in the terminal. Windows Terminal takes about 1.3 s.

- XTerm reads about a third slower through Xwayland than on its own X server, and the extra time is in XTerm itself.

- The minimap once cost about half the throughput. See the Minimap design doc.

## Roadmap

- The published speed rows want a proper run with the minimap on, since it is on by default now.

- The middle latency leg, when the render path is next opened up.

- Windows speed rows only if the console host stops being the limit. Backlog: "Terminal throughput benchmark: the Windows speed rows" (deferred, Opened 20260802-094409).

- The standing profiler hotspot is harfrust rebuilding its shape plan on every run, with no plan cache upstream. The levers are the shaping gate, a plain-ASCII fast path that skips fallback, or a plan cache offered upstream.
